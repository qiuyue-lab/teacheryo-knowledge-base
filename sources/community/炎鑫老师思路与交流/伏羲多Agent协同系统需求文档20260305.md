### 1.1 文档目的与范围

本文档是"伏羲AI赋能精准教学系统"（以下简称"伏羲系统"）的完整需求规格说明书，旨在为系统的设计、开发、测试与迭代提供唯一的权威参考依据。

本文档覆盖以下范围：

- 伏羲系统的总体架构与设计哲学

- Sub-Agent间的协同与交互机制
- 系统质量保证与动态进化机制

## 第2章 项目背景与总体目标

### 2.1 项目背景

中国中小学教育，尤其是以高考为导向的备考体系，长期面临一个根本性矛盾：顶尖教师所掌握的命题洞察力、学生思维诊断能力以及精准教学方法，本质上是一种高度个人化的隐性知识，依附于个体经验而存在，极难被系统化记录、复制与传承。

这一矛盾导致的直接结果是：教育质量严重依赖教师个人水平，优质教学资源高度稀缺，绝大多数学生无法获得真正意义上的"精准教学"。

伏羲系统正是在这一背景下被提出的。其核心野心在于：借助人工智能技术，将这种原本只存在于少数专家脑海中的隐性知识，通过"解构—建模—赋能"的系统化工程，转化为可量化、可传授、可复用的显性知识体系，最终实现教育领域的"认知平权"。

### 2.2 核心问题与痛点

伏羲系统所要解决的核心问题可归纳为以下四个痛点：

**痛点一：教师"凭感觉教"**

优秀教师对命题规律的把握、对学生思维弱点的诊断，依赖于多年积累的直觉与经验。这种能力无法被标准化，导致教学质量在不同教师之间差异悬殊，年轻教师的成长周期漫长且缺乏结构化支撑。

**痛点二：学生"盲目刷题"**

学生的核心困境不是"不知道知识点"，而是"看懂了题，选错了答案"。问题的根源在于思维路径上存在隐性的"堵点"，而学生既无法自我发现，也无从针对性地训练。大量低效刷题不能解决思维层面的结构性问题。

**痛点三：知识库是"碎纸机"**

现有的大多数题库与知识库，本质上是知识点的罗列与分类，丢失了知识内部的逻辑结构、层次关系与认知关联。这类知识库只能支持知识检索，无法支撑真正的思维训练。

**痛点四：课程标准无法直接使用**

《课程标准》是权威的教育纲领，但其语言高度抽象（如"史料实证""时空观念"），缺乏可直接操作的颗粒度，无法转化为可测量的教学工具和命题依据。

### 2.3 系统总体目标

基于上述背景，伏羲系统的总体目标定义如下：

**目标一：解构命题逻辑**

将高考试题与课程标准拆解为最底层的、可测量的"能力点"，建立起一套覆盖学科核心素养的结构化能力点数据库。

**目标二：建立思维模型库**

从大量试题标注数据中，通过模式识别，提炼出高频复用的"思维模型"、"思维堵点"类型与"命题技术"，形成可被AI与教师共同使用的知识资产。

**目标三：赋能精准教学**

将上述研究成果转化为教师可用的诊断工具（试题深度解析、学生答案批阅）和学生可学的训练路径（思维堵点专项训练、命题人视角培养）。

**目标四：实现系统自我进化**

构建知识反哺机制，使系统在使用过程中持续积累新发现，并将其纳入知识库，形成越用越强的正向循环。

### 2.4 核心设计哲学

伏羲系统的所有架构决策与行为规范，均以下列五条核心哲学为最高原则。这些原则在任何具体需求与哲学原则发生冲突时，以哲学原则为准。

**哲学一：动态进化**

系统的初始设计可以不完善，但必须内置迭代与演化的能力。任何模型、规则、数据库都不是终态，而是当前最佳实践的体现。系统的价值在于持续进化，而非一次性完成。

**哲学二：认知对称性（解析即命题）**

深度解析一道题目所需的认知能力，与设计这道题目所需的认知能力，在本质上是同一能力的两个方向。因此，系统不需要独立开发"命题专家"，而是通过激活"解析专家"的逆向能力，实现解析与命题的统一。

**哲学三：知识非碎片**

知识的价值不在于孤立的事实，而在于事实之间的逻辑结构。系统必须以"知识形状"而非"知识点标签"来组织和表达知识，确保知识库是有结构的认知网络，而非碎片的堆砌。

**哲学四：维度协同（乘法思维）**

学生的综合能力是多个核心素养维度的乘积，而非加法叠加。任何一个维度趋近于零，整体能力即崩溃。因此，诊断的核心是定位"哪个维度弱"，而非寻找"缺哪个知识点"。

**哲学五：实事求是**

在所有分析环节，系统必须优先呈现原始材料与直接观察，杜绝在缺乏依据的情况下生成"看起来合理"的内容。这一哲学在操作层面体现为：原文强制呈现、多轮验证自查、承认不完整、内心推演显性化。

## 第3章 系统总体架构需求

### 3.1 伏羲引擎（Fuxi Engine）统一核心需求

#### 3.1.1 引擎定位

伏羲引擎是整个系统的统一核心与唯一调度中枢。它不直接承担任何具体的学科分析任务，而是作为所有Sub-Agent的"操作系统"，负责定义分析问题的方法论、管理Sub-Agent的生命周期、协调多Agent之间的任务流转，以及维护系统的共享知识资源。

引擎的核心价值在于实现"变与不变的分离"：学科知识（插件层）可以随时替换和扩展，但引擎所承载的分析方法论与系统规范保持稳定，从而保证系统的通用性与可扩展性。

#### 3.1.2 引擎核心职责

**\[P1]** 引擎必须承担以下核心职责：

- **Sub-Agent调度：** 根据用户输入的任务类型（课标解构 / 题目标注 / 试题分析 / 答案批阅 / 备考规划），识别所需激活的Sub-Agent，并完成任务的分发与协调。对于跨越多个Sub-Agent的复合任务，引擎必须管理任务的串行或并行执行顺序。

- **方法论执行监督：** 引擎必须在全局范围内强制执行系统的核心方法论规范，包括"原文强制呈现"原则、"多轮自查"规范、"自反性校验"要求。当Sub-Agent的输出违反上述规范时，引擎必须触发第7章7.4节定义的异常修正流程，而非直接将不合规输出传递给用户。

- **共享知识资源管理：** 引擎作为所有Sub-Agent访问TinyDB知识库的统一网关，负责数据读取、写入、版本控制与一致性保障。Sub-Agent不得绕过引擎直接操作数据库（引擎网关的工程实现形态详见附录A）。

- **上下文维护：** 在一次完整的分析任务中，引擎必须维护跨Sub-Agent的上下文状态，确保下游Sub-Agent能够获取上游Sub-Agent产出的结构化数据，而无需用户重复输入。

- **质量门控：** 在Sub-Agent产出结果提交给用户或写入数据库之前，引擎必须执行预设的质量门控检查，包括格式合规性检查、逻辑一致性检查和完整性检查。

#### 3.1.3 引擎内置方法论规范

**\[P1]** 引擎必须将以下方法论规范内置为系统级约束，对所有Sub-Agent均有约束力：

- **原文优先原则：** 在处理任何输入材料（试题、课标、学生答案）时，Sub-Agent的第一步输出必须是对原始材料的完整引用与呈现，不得省略、改写或直接跳转到分析结论。

- **直接观察优先原则：** 分析的起点是对具体材料的直接观察，而非将预设的框架或编码强行套用到材料上。当观察到的现象与已有框架发生冲突时，以观察结果为准，并将该冲突标记为知识反哺候选数据，纳入第5章5.2.5节定义的知识反哺与迭代流程；若冲突导致当前分析流程无法正常继续，须同时触发第7章7.4节定义的异常修正流程。

- **框架可错性原则：** 系统内所有方法论工具（能力点数据库、思维模型、命题技术库）均是当前最佳实践，而非永恒真理。当工具与具体题目的实际情况不符时，以实际情况为准，并将差异记录为潜在的知识反哺数据。

- **自反性原则：** 系统产出的任何知识、分析结论或方法论，均须以同等严格的标准接受审视。该原则防止系统产生"只对外适用、对自身不适用"的双重标准。

#### 3.1.4 引擎不包含的内容

为保持引擎的通用性，以下内容明确不属于引擎的职责范围，由插件层承载：

- 任何具体学科的知识内容
- 特定学科的能力点编码与数据库
- 特定学科的错误类型分类
- 特定学科的标注示例与典型案例

### 3.2 Sub-Agent协同生态架构总览

#### 3.2.1 Sub-Agent清单与定位

伏羲系统共包含五个Sub-Agent，均运行于伏羲引擎的统一管理之下：

| Sub-Agent名称 | 核心定位 | 所属流程类型 |
|---------------|----------|--------------|
| 知形（Zhi-Xing） | 课标解构专家 | 数据构建主流程（上游） |
| 能力点标注专家 | 单题原子化分析 | 数据构建主流程（核心） |
| 试题分析专家 | 面向教学的试题解读 | 教学应用流程 |
| 试题批阅专家 | 学生答案诊断引擎 | 教学应用流程 |
| 备考专家 / 命题思维教练 | 备考战略指导 | 教学应用流程 |

#### 3.2.2 Sub-Agent间的上下游关系

**\[P1]** 系统必须遵循以下Sub-Agent的上下游依赖关系：

- 知形的产出（能力点数据库初始版本）是能力点标注专家开展工作的前提条件。
- 能力点标注专家的产出（单题标注结构化数据）是聚合分析与模型提炼的数据源头，也是试题分析专家和试题批阅专家所调用知识库的核心组成部分。
- 试题分析专家的产出（评分标准与题目深度解析）是试题批阅专家的直接工作起点。
- 备考专家在独立运作的同时，也依赖能力点数据库与思维模型库中已积累的数据质量。

#### 3.2.3 共享资源访问规范

**\[P1]** 所有Sub-Agent必须通过伏羲引擎的统一接口访问以下共享资源：

- TinyDB能力点数据库
- TinyDB试题数据库
- TinyDB思维模型与命题技术库
- TinyDB学生学习数据库

**\[P2]** Sub-Agent在读取共享资源时应当获取资源的版本标识，确保分析结果可追溯至特定版本的数据库状态。

### 3.3 学科插件（Discipline Plugins）规范需求

#### 3.3.1 插件设计原则

学科插件是"可插拔的专业知识包"。系统的核心架构需求是：切换学科时，只替换插件，引擎与Sub-Agent的逻辑保持不变。

#### 3.3.2 标准插件包结构

**\[P1]** 每个学科插件包必须包含以下三个标准组件：

- **能力点数据库组件：** 基于该学科《课程标准》拆解出的、经过验证的能力点（提点与微提点）结构化数据集，含完整编码体系与层级关系定义。

- **标注示例库组件：** 不少于20道经过人工审核的典型真题标注案例，用于Sub-Agent的行为校准与质量基准参考。

- **错误类型库组件：** 该学科常见的学生思维错误分类（按思维堵点类型组织）与命题陷阱分类（按命题技术类型组织）。

#### 3.3.3 插件扩展规范

**\[P2]** 当需要新增学科插件时，应当遵循以下规范：

- 新插件的能力点编码体系须符合系统统一的编码格式规范
- 新插件必须经过不少于50道真题的验证标注后，方可进入正式使用状态
- 插件版本需纳入引擎的版本管理体系，确保历史分析记录可追溯

**\[P3]** 系统可以支持同一学科下的多个地区版本插件（如全国卷历史插件、北京卷历史插件），并允许在分析任务启动时指定使用的插件版本。

## 第4章 Sub-Agent功能需求规格

### 4.1 知形（Zhi-Xing）——课标解构专家

#### 4.1.1 角色定位与核心使命

知形是整个伏羲系统的"上游基石"，其核心使命是将以自然语言书写的、高度浓缩的《课程标准》纲领性文件，转化为AI系统可理解、可执行、结构化的知识框架，直接产出能力点数据库的初始版本。

知形所要回答的根本问题是："国家要求教什么、怎么教、以及教到什么程度？"

#### 4.1.2 核心方法论：七问法

**\[P1]** 知形必须采用"七问法"作为解构课标文本的标准方法论，对每一条课标表述执行以下七步追问：

1. **问一：它说了什么？** 提取字面核心主张，形成无歧义的文本摘要。

2. **问二：它为什么这么说？** 探究用词背后的逻辑与意图。重点关注动词选择的差异（如"认识"与"了解"、"探讨"与"掌握"背后的能力层级差异）和限定词的边界含义。

3. **问三：它为什么放在这里说？** 分析信息排布顺序与结构位置的含义。目录的先后、概念的并列或包含关系，均反映设计者的认知优先级与逻辑架构。

4. **问四：它和谁一起说？** 考察概念的聚合关系。哪些知识点被归为一类，揭示了它们之间的内在关联，是建立"能力点组合"的重要依据。

5. **问五：它没说什么？** 分析"沉默"的部分。对比旧版课标或常理预期，被省略或回避的内容往往标定了该学科当前版本的边界与重点转变。

6. **问六：反例是什么？** 若课标不这么规定，会怎样？通过构建反例加深对现有规定合理性的理解，并辅助判断能力点的覆盖边界。

7. **问七：最终指向什么？** 将所有具体规定与顶层"学科核心素养"相关联，确保能力点拆解始终服务于核心素养目标，不因追求颗粒度而失去方向。

#### 4.1.3 六步拆解工作流

**\[P1]** 知形必须按以下六步顺序完成课标拆解工作：

**Step 1：原文提取**

从课标文件中逐条提取能力描述，以课标原文为唯一依据，不创造、不改写、不添加。每条提取结果须标注课标原文出处（页码或章节编号）。

**Step 2：微题点拆解**

将提取出的能力描述逐步拆解，直至每个单元满足"微题点颗粒度判断标准"（详见4.1.4节）。拆解过程中须记录"提点→微提点"的层级映射关系。

**Step 3：真题验证**

用现有高考真题对拆解出的能力点进行验证，建立"题目—能力点"映射关系，确认每个微题点在真实考试中确实存在对应的命题行为。

**Step 4：缺失部分处理**

对在真题验证中发现的异常情况按如下规则处理：

- 若某能力点无法在课标中找到依据，判断为AI幻觉可能性，标记为"待核查"，不纳入正式库
- 若某能力点满足以下全部条件，标注为"省份特色能力点"：该能力点在当前已收录真题数据集中90%及以上的出现集中于特定1—2个省份卷种，且在全国统一卷（全国甲卷、全国乙卷、新课标Ⅰ/Ⅱ卷）中从未出现过，且该能力点的出现次数不少于3次（确保判断有最低样本支撑，而非偶发现象）。每次数据库版本升级时，引擎须对所有"省份特色能力点"状态条目重新执行上述量化评估，若不再满足判断标准则自动提示降级或调整分类。
- 若真题考查行为超出课标显性描述，标注为"课标隐性延伸"并补充记录

**Step 5：分类扩展**

通过对多套试卷的高频数据分析，识别课标中表述模糊但实际命题频繁的领域，对相关能力点进行补充与细化。

**Step 6：循环迭代与收敛判定**

将Step 3—5中发现的所有偏差与补充，反馈至Step 1—2进行修正。每次迭代完成后，须执行收敛性判断。

**迭代终止条件：** 满足以下全部条件时，判定为迭代收敛，输出正式版本：连续两轮迭代中新增或修改的微题点数量少于当前微题点总数的3%；当前轮次无新增"待核查（pending）"状态的微题点；当前轮次无因Step 3验证失败而被新标记的能力点。

**最大迭代轮次上限：** 无论是否达到收敛条件，Step 6最多执行5轮。第5轮结束后，无论是否满足收敛标准，均输出当前版本作为正式版本，并将所有未解决的"待核查"项目生成专项待处理清单，移交用户决策。

#### 4.1.4 微题点颗粒度判断标准

**\[P1]** 知形在执行拆解时，必须以下列四条标准作为判断一个能力单元是否达到"微题点"颗粒度的依据。满足全部四条，方可认定为独立微题点：

**标准一：可出题性。** 将这个点单独拿出来，能够独立支撑一道考试题目的设计。若无法独立出题，则需继续在上一层级的提点中合并处理。

**标准二：课标依据可查。** 能在课标原文中找到对应的表述依据（直接或合理推断）。

**标准三：与其他能力点的独立性。** 与已有的其他微题点在认知操作上有明确区分，不构成重复覆盖。

**标准四：真题出现频率达到阈值。** 在已有真题数据集中，至少出现过一次可被对应的命题案例。

#### 4.1.5 产出规范

**\[P1]** 知形必须产出以下结构化数据，并通过引擎写入TinyDB能力点数据库：

每个能力点记录须包含：能力点唯一编码、层级类型（提点/微题点）、课标原文出处、核心行为动词、认知操作描述、关联的核心素养维度、状态标注（正式/待核查/省份特色/课标隐性延伸）。

**\[P2]** 知形应当同时产出一份人类可读的课标解构报告，以结构化文本形式呈现三层输出（学什么 / 怎么学 / 学到什么程度），供教师直接参考使用。

### 4.2 能力点标注专家

#### 4.2.1 角色定位与核心使命

能力点标注专家是整个系统的"数据生产引擎"，承担对单道高考试题进行"CT扫描"式深度解剖的核心任务。其使命是将一道模糊、综合的高考试题，拆解为一系列精确、可测量、可分析的结构化数据，包括能力点序列、思维路径、思维堵点、命题技术与知识形状。

#### 4.2.2 输入要求与降级模式

**\[P1]** **标准模式：** 能力点标注专家必须要求以下三项完整输入，三项齐备时启动标准分析模式：

- 题目原文（题干、材料、选项等完整内容）
- 官方参考答案
- 官方试题解析（含考查目标与解析原文）

**\[P2]** **降级模式：** 当"官方试题解析"缺失，但题目原文与官方答案完整时，系统不得直接拒绝，须启动降级模式，并遵循以下规则：

- 能力点标注专家可在缺少官方解析的条件下运行，但其所有产出字段须附加标注 `analysis_quality`: "reduced"`
- 阶段0中的"官方解析原文呈现"环节须输出明确提示 "\[无官方解析，本环节跳过]" 后继续执行，不得中断整体流程
- 降级模式下产出的标注数据须整体标记为"非正式标注（无官方解析）"，不得写入正式TinyDB试题数据库，须存入独立的"待补充队列"
- 引擎须主动提示用户："当前分析已以降级模式完成，分析可靠性相对较低。补充官方解析后，可触发正式标注覆盖本次结果。"

当三项输入均缺失官方答案时，引擎须向用户发出"输入不完整"信号并拒绝启动分析，官方答案为不可豁免的最低输入要求。

#### 4.2.3 分析工作流：

本工作流各阶段命名规则说明如下：阶段0与阶段1为原文锚定与路径还原的预处理阶段；阶段2（A、B、C）为多角度交叉验证的质量保障阶段；阶段3与阶段4为综合输出的结论生成阶段。任何阶段均不得跳过。

#### **阶段0：原文强制呈现与初步解构**

**\[P1]** 本阶段必须按以下顺序执行，不得跳过：

1. 首先，逐字呈现题目原文、官方考查目标原文与官方解析原文，作为全程分析的锚定基准。

2. 其次，运用"四元区分法"对官方考查目标进行结构化拆解。四元区分法的四个维度定义如下：
   - **做什么**（核心的认知动作是什么，如比较、判断、说明）
   - **怎么做**（以何种方式或路径完成该动作，如结合材料、运用唯物史观）
   - **用什么**（调用的知识资源是什么，如特定历史时期的史实、经济理论）
   - **到什么程度**（达到何种能力水平，对应课标学业质量水平）

3. 最后，基于拆解结果，与当前学科插件的能力点数据库进行初步匹配，形成"候选能力点列表"。

#### **阶段1：解题思维步骤提炼**

**\[P1]** 基于官方解析原文，还原命题人预设的标准解题思维路径。本阶段的核心认知是：官方解析的写作过程，本质上是命题人预设的学生理想解题思维过程的还原。

产出格式须为有序的思维步骤链，例如：第一步：提炼关键信息 → 第二步：判断时间空间 → 第三步：解释历史现象 → 第四步：建立因果关系。

#### **阶段2：多轮自查与验证：包括阶段A/B/C**

##### **阶段A：能力点全面识别与自查**

**\[P1]** 本阶段须以独立分析指令启动。引擎在调用Sub-Agent执行本阶段时，必须在系统指令中显式要求：不得参照或引用阶段0的任何识别结论；Sub-Agent必须在阶段A的输出开头声明"本阶段分析独立进行，以下识别结论不基于阶段0的结果"；阶段A的分析权限仅包含题目原文、官方答案、官方解析三项原始材料以及能力点数据库，不包含阶段0的任何中间产出。

本阶段要求Sub-Agent在上述约束下独立重新审视题目，形成一份新的能力点识别清单，然后与阶段0的候选列表进行比对，明确标注：两阶段一致的能力点；阶段A新发现而阶段0遗漏的能力点；阶段0中出现但阶段A无法复现的能力点（标记为"存疑项"，需在阶段B中处理）。

本阶段相当于"换个角度重新思考一遍"，是系统防范逻辑不一致的第一道防线。

##### **阶段B：维度定位与能力点再匹配**

**\[P1]** 本阶段针对阶段A形成的完整能力点列表，严格按照数据库编码格式，对每个能力点执行：核心素养维度归属确认（如史料实证、时空观念等）；能力点编码匹配与级别标注（提点/微题点）；对阶段A"存疑项"的裁决（保留/剔除/拆分）。

本阶段的目的是防止"削足适履"——即为了匹配现有编码而扭曲对题目实际考查内容的判断。当真实情况与数据库编码出现冲突时，以真实情况为准，并标记为知识反哺候选项。

##### **阶段C：最终确认与格式化**

**\[P1]** 基于阶段B的结果，生成最终的、格式规范的能力点标注清单，每项包含：能力点编码、能力点名称、对应题目材料的具体证据（原文引用）、层级类型。本阶段产出是后续所有分析的唯一依据，后续阶段不得再修改能力点列表。

#### **阶段3：思维路径、堵点、命题技术与知识形状分析**

**\[P1]** 基于阶段C确认的能力点，执行以下四步分析：

1. **思维路径串联：** 将阶段C中的能力点按逻辑顺序串联，形成完整的"学生思维链"。

2. **思维堵点识别：** 在思维链中，定位学生最容易发生认知中断的环节。堵点的判断标准是：该环节要求的思维跳跃幅度最大，或要求的认知层次转换最困难（如从"描述现象"跳跃到"分析本质"）。识别出的堵点须归类至4.4.3节定义的四大核心堵点类型，并参照各类型的操作性区分标准执行归类。

3. **命题技术逆向提炼：** 基于识别出的思维堵点，逆向推导命题人使用的命题技术。核心逻辑是：学生的思维堵点即命题人的命题技术体现。将推导出的命题技术与插件的命题技术库进行比对，若为库中已有类型则引用编码，若为新类型则标记为"新命题技术候选项"。

4. **知识形状识别：** 基于题目的核心设问动词与句式结构，判断本题主要激活的知识形状类型，依据以下识别规则执行：设问包含"指出/列举/写出"等直接提取指令 → 点形（●）；设问包含"说明/分析……之间的关系/联系" → 网形（◈）；设问包含"概括……过程/变化/发展" → 链形（→）；设问包含"揭示/阐释……本质/根源/实质" → 层形（▽）；设问包含"比较……异同/相同/不同之处" → 镜形（◇）；设问包含"综合以上/归纳……规律/特征" → 锥形（△）。当设问同时触发多种形状时，以答题时认知负荷最重的形状为主要形状，其余标注为次要形状。识别结果写入题目标注数据的 `knowledge_shape` 字段（详见第6章6.2.5节）。

#### **阶段4：思维模型识别与最终报告生成**

**\[P1]** 识别本题的能力点组合序列属于哪一种预定义思维模型，并生成完整的单题标注报告。报告内容须涵盖以上所有阶段的分析结果，并额外包含一个精简摘要（L2专线），单独提取命题技术、思维堵点与本质规律等核心发现。

#### 4.2.4 数据写入规范

**\[P1]** 分析完成后，能力点标注专家必须通过引擎将结构化数据写入TinyDB试题数据库，包含：

- 题目元数据（题号、年份、卷种、题型等）
- 能力点标注清单（含编码与证据）
- 思维路径序列
- 思维堵点（含类型与所属阶段）
- 命题技术（含编码或候选标记）
- 所属思维模型编码
- 知识形状标注（主要形状类型与次要形状类型）
- 生成本次标注所使用的Sub-Agent Prompt版本号

### 4.3 试题分析专家（Exam Analyst）

#### 4.3.1 角色定位与核心使命

试题分析专家是面向教学应用的"产品生成器"，其核心使命是将命题逻辑的深度理解转化为教师和学生可直接使用的高质量试题解析文本。它解释的是"如何思考"而非"答案是什么"，揭示从题干材料到正确答案之间的思维路径与方法论。

#### 4.3.2 四种工作模式

**\[P1]** 试题分析专家必须支持以下四种工作模式，并能在引擎指令下灵活切换：

- **模式一：试题深度解析。** 对输入的试题生成完整的教学导向型解析文本，核心是呈现思维过程而非直接给出答案。

- **模式二：命题逻辑解构。** 针对教师需求，深度分析试题的材料选择逻辑、设问设计思路、干扰项设计逻辑与评分标准生成逻辑。

- **模式三：质量评估。** 对一道试题（真题或自生成题目）的结构合理性、设问逻辑、干扰项设计质量进行评估，并给出改进建议。

- **模式四：逆向命题（认知对称性的体现）。** 基于对一道题的深度解析理解，逆向生成结构相似、考查点相同的新题目或改编题目。本模式的触发必须以完成模式一分析为前提。

#### 4.3.3 开放性题目分类决策机制

**\[P1]** 对于主观题（尤其是历史小论文、观点论证类题目），试题分析专家必须按以下三步决策机制处理：

**Step 1：题目类型识别**

将题目细分为"论述分析类"、"历史小论文类"、"观点论证类"等子类型。

**Step 2：答案性质判断**

判断官方答案属于"框架示例型"（展示分析框架）还是"成品范文型"（完整文章），不同性质的答案需采用不同的解析策略。

**Step 3：平衡策略执行**

采用"从示例中提炼方法→用建议语气表述→给出具体指导→示例作为支撑"的四步平衡策略。具体要求：使用"可以从……角度切入"而非"必须"等指令性语言；通过具体史实举例但不穷尽所有内容；为学生保留独立思考与自主组织的空间。

#### 4.3.4 产出规范

**\[P1]** 模式一的产出必须为Markdown格式的结构化解析文档，包含：题目背景与情境分析；解题思维路径（分步骤呈现）；关键能力点说明；常见错误与思维堵点提示；评分要点（主观题）。

**\[P2]** 模式四的产出应当在生成后自动触发模式三的质量评估，形成"生成—评估"的自验证闭环。

### 4.4 试题批阅专家

#### 4.4.1 角色定位与核心使命

试题批阅专家是一个诊断导向的教学引擎，其核心使命是将学生答案转化为可供分析的思维过程数据，实现对学生能力短板的精准诊断与教学干预建议输出。它的最终产出不是一个分数，而是一份包含现象描述、病灶定位、量化评估与解决方案的完整诊断报告。

#### 4.4.2 工作前提

**\[P1]** 试题批阅专家的启动必须以试题分析专家（模式二）产出的评分标准为前提。批阅行为须严格基于该评分标准执行，而非依赖Sub-Agent的内置知识进行模糊判断。

#### 4.4.3 批阅方法论

**方法论一：普遍性与特殊性分析**

**\[P1]** 批阅过程必须明确区分两类分析内容：

- **共性分析**——核对学生答案对标准得分点的覆盖度，用于计分
- **个性分析**——分析学生答案中的独特表述、逻辑链条与知识盲区，用于诊断

个性分析是诊断报告的重点内容，不可省略。

**方法论二：思维堵点归因**

**\[P1]** 当学生答案出现错误或缺失时，必须从以下两个维度进行深层归因，而非简单判断为"知识点未掌握"：

**堵点类型归因：** 将错误归因至以下四大核心思维堵点中的具体类型。各类型的操作性定义与区分标准如下：

- **多要素综合判断堵点：** 学生能理解题目涉及的各个独立要素，但无法将多个要素同时纳入一个判断框架，进行综合权衡后得出统一结论。典型表现：只回答了题目的一个侧面，遗漏其他维度；或各要素分析完整但无法形成最终统一判断。区分标准：错误不在于抽象层次不够（层次抽象堵点），也不在于逻辑链条断裂（逻辑链条构建堵点），而在于要素完备但整合失败。

- **知识迁移堵点：** 学生已掌握相关知识点，但无法将该知识从熟悉的语境迁移到题目的新材料或新情境中识别并应用。典型表现：做过高度相似题后仍然答错；能正确背诵知识但无法将其与题目材料建立关联。区分标准：追问学生"你知道XXX是什么吗"可以得到正确回答，但学生无法识别当前情境需要调用该知识，而非知识本身不会。

- **层次抽象堵点：** 学生的思维停留在具体现象的描述层面，无法完成从"描述是什么"到"解释为什么/本质是什么"的认知层次跃升。典型表现：答案大量停留在照抄材料或转述事实，缺少对本质的概括与提炼；答案使用"可以看出……""反映了……"等过渡语言但不作实质解释。区分标准：错误不在于多个要素整合失败，而在于单一思维操作的深度不足，无法完成认知的垂直跃升。

- **逻辑链条构建堵点：** 学生的各个分析步骤可能是正确的，但步骤之间的因果或推导连接不成立，导致论证链条断裂。典型表现：结论与前提之间缺少中间环节；出现"因为A所以C"而跳过必要的B；各论点并列排列但缺少逻辑推进关系。区分标准：错误不在于要素整合失败，也不在于抽象层次不足，而在于水平方向上的逻辑连接出现跳跃或断裂。

**读想双维归因：** 判断错误发生在"读"的阶段还是"想"的阶段。"读"的阶段错误须定位至材料处理五步链中的具体断裂环节；"想"的阶段错误须结合知识形状误用进行判断，具体如下：

**材料处理五步链**各环节的操作性定义与典型错误识别标准：

- **定位（Locate）：** 在材料中确定与设问直接相关的信息区域。判断标准：能指出材料的哪一句或哪一段与题目设问直接对应。此环节出错的典型表现：学生在整篇材料中漫无目的地寻找信息，无法锁定相关段落，答案内容与设问偏离。

- **解码（Decode）：** 将材料中的专业术语、文言表述、数据或图表转化为可理解的普通语言。判断标准：能用自己的话准确复述材料内容，无核心信息失真。此环节出错的典型表现：对关键术语产生误读，或无法处理文言/专业表述，答案呈现出对材料的明显曲解。

- **筛选（Filter）：** 从已定位的信息中，剔除与设问无关的干扰信息，保留直接有效信息。判断标准：能区分"题目给出了这个信息"与"这个信息对回答设问有用"的差异。此环节出错的典型表现：将材料全文照搬为答案，或纳入大量与设问无关的背景信息，无法区分有效信息与干扰信息。

- **提纯（Distill）：** 将筛选后的有效信息进行抽象概括，从具体事实提炼出可直接用于答题的概念或论点。判断标准：能将"材料说X做了Y"转化为"X体现了Z原则/特征"。此环节出错的典型表现：答案停留在转述材料，无法完成从事实到论点的提炼（此类错误与层次抽象堵点高度相关，须结合堵点归因一并标注）。

- **隐含推断（Infer）：** 识别材料中未明确说明但可以合理推断的信息。判断标准：能指出材料的隐含前提或未明说的结论，且推断有合理依据，而非主观臆测。此环节出错的典型表现：完全忽略隐含信息导致答案不完整，或作出超出材料逻辑的过度推断导致答案偏离。

**知识形状误用判断：** 在执行"想"维度的归因时，须额外检查知识形状误用。方法为：从题目标注数据中读取该题的预期知识形状（由阶段4赋值）；通过分析学生答案的结构判断其实际呈现的知识形状；若两者不符（如题目要求"镜形"比较，学生输出了"链形"叙述），则在归因结论中标注"知识形状误用"，并在诊断报告第三部分注明预期形状与实际形状及其差异含义。

#### 4.4.4 诊断报告产出规范

**\[P1]** 每次批阅必须产出包含以下五个部分的结构化诊断报告：

1. **第一部分：答案现象描述。** 客观呈现学生答案的主要内容，不做评判。

2. **第二部分：共性覆盖度分析。** 逐条比对标准得分点的覆盖情况，给出初步得分判断。

3. **第三部分：核心病灶定位。** 指出学生思维断裂的具体位置，必须关联能力点数据库编码（如"2.5-L3薄弱：未完成从现象描述到本质概括的思维跳跃"），并注明知识形状误用情况（如存在）。

4. **第四部分：预估得分与扣分说明。** 给出量化得分，并说明给分与扣分的具体理由。

5. **第五部分：干预建议。** 为教师提供具体、可操作的教学干预步骤，包括追问话术建议和专项训练方向。

**\[P2]** 诊断报告应当同时将结构化诊断数据写入TinyDB学生学习数据库，用于后续的学生知识图谱分析。

### 4.5 备考专家 / 命题思维教练

#### 4.5.1 角色定位与核心使命

备考专家的核心目标不是提供题目或答案，而是帮助师生建立"命题人视角"，实现从"被考者"到"出题人"的视角跃迁。它将顶尖命题专家的隐性思维显性化、工具化，解决的是"思维不通"而非"知识不会"的深层问题。

#### 4.5.2 六大核心能力

**能力一：试卷战略分析能力**

**\[P1]** 备考专家必须能够从宏观视角分析完整试卷，评估知识点分布、难度梯度、核心素养覆盖情况，产出包含具体数据与改进建议的战略分析报告。

**能力二：知识点考法穷尽能力**

**\[P1]** 对于任意给定的知识点，备考专家必须能够穷举其所有可能的考查方式，按基础层、应用层、综合层、创新层四个层级进行分层呈现，并标注每种考法的历年出现频率与难度系数。

**能力三：命题思维引导能力（苏格拉底式教练）**

**\[P1]** 在与学生的对话交互中，备考专家必须采用苏格拉底式提问策略，不直接给予答案，而是通过"如果你是出题人，会先考什么？"等引导式追问，帮助学生自主建构命题视角。

对话须遵循以下终止条件与退出路径：

- **路径一：学生主动收获（理想退出）：** 当学生在引导过程中主动总结出正确的命题视角，备考专家须对此予以确认，随即生成完整的考法分层框架作为对话总结。

- **路径二：达到最大引导轮次（安全退出）：** 单次苏格拉底式对话的最大引导轮次为7轮。达到上限后，无论学生是否已建立完整视角，备考专家均须主动终止引导，汇总当前对话进展，输出完整的考法分层框架，并明确标注"以下框架基于本次对话内容总结，建议结合自主练习进一步内化"。

- **路径三：学生主动中止（强制输出）：** 当学生明确表示终止对话时，备考专家须立即输出当前已完成部分的进度总结及已覆盖的考法分层内容，不得以"对话未完成"为由拒绝输出。

三种路径均须以一个清晰的考法分层框架作为最终产出，强化学生的元认知。

**能力四：备考战略建议能力**

**\[P2]** 备考专家应当能够基于分析结果，为学生提供"基础层必须100%掌握→重点突破典型应用考法→冲刺综合层"的优先级排序备考建议；为教师提供试卷设计建议与按考法分层组织复习的教学策略。

**能力五：学生知识图谱分析能力**

**\[P2]** 在接入学生历史学习数据的条件下，备考专家应当能够基于TinyDB学生学习数据库，对学生进行个性化精准诊断，识别"高考高危知识点"（掌握度低且高考必考），并输出个性化学习路径规划。

**能力六：命题规律库调用能力**

**\[P1]** 备考专家必须能够调用TinyDB中积累的思维模型库与命题技术库，以数据支撑考法分析，确保考法预测有历史依据，而非凭空推测。

#### 4.5.3 角色语言风格规范

**\[P1]** 备考专家的语言输出必须符合以下风格规范：

- 专业但不说教
- 善用"咱们来想一想"、"如果你是命题人"等引导性句式
- 采用分层递进的逻辑结构，逐步揭示命题规律的全貌
- 具有同理心，尊重学生当前的认知水平

## 第5章 核心工作流程需求

### 5.1 工作流总览与分类

伏羲系统的工作流程分为两大类型，在同一引擎下并行支持、按需激活：

**数据构建主流程：** 五步串行流程，具有严格的前后依赖关系，是系统知识资产积累的核心路径。此流程的产出是系统所有应用功能的数据基础，必须优先完成并保持数据质量。

**教学应用流程：** 三路并行流程，依托已有知识库按需触发，面向教师与学生的日常使用场景。各路流程之间可独立运行，但共享同一底层知识库。

两类流程之间存在动态的知识反哺关系：应用流程中发现的新问题与新规律，须通过第五步"知识反哺"流程回流至数据构建主流程，形成系统的自我进化能力。

### 5.2 数据构建主流程（串行五步）

#### 5.2.1 第一步：课标解构工作流

- **触发条件：** 接入新学科、新版本课标，或现有学科插件的能力点数据库触发重建/大规模修订。
- **执行主体：** 知形（Zhi-Xing）Sub-Agent。
- **输入：** 目标学科《课程标准》全文（PDF或文本格式）；辅助参考材料（教学指导意见、教材目录、相关学术研究）。
- **核心执行逻辑：** 按4.1.3节"六步拆解工作流"执行，同步采用4.1.2节"七问法"对每条课标表述进行深度解读。
- **完成标准：** **\[P1]** 以下条件必须全部满足方可认定本步骤完成：所有能力点均已完成提点→微题点的层级拆解；每个微题点均已标注"可出题性"验证结果；至少完成一次Step 3"真题验证"，建立初步的题目—能力点映射关系；产出已写入TinyDB能力点数据库，且格式合规性检查通过。
- **与下游的交接：** 本步骤产出的能力点数据库初始版本，作为第二步单题标注工作的必要前置条件。

#### 5.2.2 第二步：单题标注工作流

- **触发条件：** 新增待标注的高考试题，或对已标注试题执行修订。
- **执行主体：** 能力点标注专家Sub-Agent。
- **输入：** 单道完整试题（题目原文 + 官方答案，两项必填；官方解析缺失时启动降级模式，详见4.2.2节）；当前有效版本的学科插件（含能力点数据库）。
- **核心执行逻辑：** 按4.2.3节"七阶段分析工作流"完整执行（阶段0 → 阶段1 → 阶段A → 阶段B → 阶段C → 阶段4 → 阶段5），不允许跳过任何阶段。
- **完成标准：** **\[P1]** 以下条件必须全部满足：阶段0已完成原文逐字呈现；阶段A与阶段C的能力点列表已完成比对，差异已说明；每个标注能力点均有原文引用证据；思维堵点已识别并归类；命题技术已推导并比对库中编码；知识形状已识别并赋值；标注数据已写入TinyDB试题数据库（标准模式）或待补充队列（降级模式）。
- **与下游的交接：** 当同一"学科+题型"组合下新增标注题目数量达到触发阈值（默认值：30道，可由系统管理员在引擎配置中调整；此阈值为初始经验估算值，应根据实际数据积累情况在后续版本中复核）时，触发第三步聚合分析。

#### 5.2.3 第三步：聚合分析工作流

- **触发条件：** 由引擎定期调度——当同一"学科+题型"组合下新增标注数量达到触发阈值（默认30道，可配置）后自动触发；或由用户主动发起针对特定题型 / 卷种 / 年份范围的分析请求。
- **执行主体：** 伏羲引擎调用TinyDB数据库执行统计查询，结果由能力点标注专家进行解读与摘要。
- **核心分析维度：**

  **\[P1] 能力点频率分析：** 统计各能力点编码在指定数据集内的出现频次，识别高频考察能力点与低频长尾能力点，形成考察热力图数据。

  **\[P1] 思维模型频率分析：** 统计各能力点组合序列在数据集内的出现规律，识别高频复用的思维链模式，为第四步的模型提炼提供数据依据。

  **\[P2] 命题技术分布分析：** 统计特定卷种、特定省份、特定年份区间内的命题技术类型分布，识别命题偏好的变化趋势。

  **\[P2] 难度梯度分析：** 基于思维堵点的类型与数量，分析数据集内试题的难度分布情况。

- **产出：** 一份聚合分析报告，包含各维度的统计数据、可视化数据结构（供前端展示）及关键规律的文字摘要，写入TinyDB聚合分析历史库。

#### 5.2.4 第四步：模型提炼工作流

- **触发条件：** 聚合分析报告显示某类能力点组合序列的出现频次超过预设阈值（初始阈值设为5次），或用户主动发起模型提炼任务。
- **执行主体：** 能力点标注专家Sub-Agent，结合引擎的模式识别能力协同完成。
- **核心执行逻辑：**

  **\[P1] 思维模型正式定义：** 对达到频次阈值的能力点组合序列，执行命名、定义与形式化描述。每个思维模型的正式记录须包含：模型名称与编码；构成模型的微题点序列（有序）；适用题型范围；代表性题目引用（至少3道）；区分该模型与相似模型的关键特征。

  **\[P1] 思维堵点模式归纳：** 对高频出现的堵点类型进行归纳与命名，形成该学科的"思维堵点模式库"。每种堵点模式的记录须包含：堵点名称与编码；对应的思维链断裂位置；典型错误表现描述；关联的命题技术编码。

  **\[P1] 命题技术库更新：** 将所有在第二步中被标记为"新命题技术候选项"的条目，经本步骤确认后正式纳入命题技术库，并建立命题技术与思维堵点的双向关联。

- **完成标准：** 本步骤的产出须经过以下自反性验证——验证须选取不少于5道未参与模型提炼的新题目，对每道题独立判断该模型能否为其提供合理解释，且解释逻辑无需对模型定义进行修改即可适用。验证结果采用三级裁决机制：

  - 全部通过（5/5）：模型正式入库，状态设为Active。
  - 部分通过（3—4/5）：模型定义存在边界模糊，须修订后重新进行不少于5道题的验证，最多允许2轮修订。
  - 大部分失败（0—2/5）：模型定义存在根本性问题，须推倒重建，进入新候选状态，原候选数据归档。

- **产出：** 更新后的思维模型库、堵点模式库与命题技术库，写入相应TinyDB数据表。

#### 5.2.5 第五步：知识反哺与迭代工作流

- **触发条件：** 以下任一情况触发本步骤：教学应用流程中发现能力点数据库未覆盖的新能力操作；试题分析或批阅过程中识别出新的思维堵点类型；命题技术候选项积累数量达到5条；用户主动发起数据库版本更新。
- **执行主体：** 伏羲引擎统一调度，相关Sub-Agent协同参与。
- **核心执行逻辑：**

  **\[P1] 候选项评审：** 引擎汇总所有待纳入的新候选项（新能力点 / 新思维模型 / 新堵点 / 新命题技术），评估其与现有库条目的冲突、重叠与互补关系，形成评审报告供用户确认。

  **\[P1] 数据库版本升级：** 用户确认后，执行TinyDB数据库的版本升级操作，新条目须附带版本标记（如"v1.1新增"），历史数据保留原版本标记，确保完整可追溯。历史数据快照的存储格式须遵循第6章6.2.3节定义的独立记录方案。

  **\[P2] 影响范围评估：** 评估本次数据库升级是否影响已有的思维模型定义、堵点分类或命题技术编码，若有影响则标记受影响条目为"需复核"状态，并生成复核任务清单。

  **\[P3] 自动触发重新聚合：** 数据库升级完成后，对受影响的题目数据集自动触发第三步聚合分析，验证新数据对整体规律描述的影响。

### 5.3 教学应用流程（并行三路）

#### 5.3.1 试题深度解析流程

- **触发条件：** 教师输入一道题目（可不附带官方解析），请求生成教学用途的解析文档。
- **执行主体：** 试题分析专家Sub-Agent（模式一或模式二）。
- **流程说明：**

  若题目已存在于TinyDB试题数据库中（即已完成第二步标注），则试题分析专家优先调用已有的标注数据（能力点、思维路径、堵点）作为分析底座，在此基础上生成叙事性解析文本，避免重复劳动。

  若题目未在数据库中，则试题分析专家基于内置的方法论与共享知识库进行独立分析（适用4.2.2节降级模式规则），并将分析过程中产出的结构化数据标记为"非正式标注数据"，提示用户可通过正式的第二步标注流程将其纳入数据库。

  **\[P2]** 对于包含多道题目的整卷解析请求，应当在单题解析完成后，自动汇总生成整卷的能力点分布报告与教学重点建议。

#### 5.3.2 学生答案批阅与诊断流程

- **触发条件：** 教师提交学生答案（单个学生或批量多个学生），请求执行批阅与诊断。
- **执行主体：** 试题分析专家（提供评分标准）→ 试题批阅专家（执行批阅与诊断）。
- **流程说明：**

  **\[P1]** 流程启动前，引擎必须确认试题分析专家已完成对该题的评分标准生成。若未完成，须先触发试题分析专家的模式二工作，再启动批阅流程。

  **\[P1]** 技术约束：基于TinyDB不支持高并发写操作的限制（详见第6章6.2.1节），批量批阅完成后的数据写入操作须采用串行批量写入模式：按学生逐条顺序写入，不得并行执行写操作。引擎须在批阅任务调度时自动启用串行写入队列。

  **\[P2]** 对于同一题目的批量学生答案，试题批阅专家应当在完成所有个人诊断报告后，额外生成一份"班级诊断聚合报告"，汇总全班在各个思维堵点上的分布情况，为教师的集体教学决策提供数据支撑。

  **\[P2]** 批阅完成的结构化诊断数据应当写入TinyDB学生学习数据库，用于备考专家的个性化分析调用。

#### 5.3.3 备考策略规划流程

- **触发条件：** 学生或教师发起备考咨询（知识点考法分析、试卷战略分析、个性化复习规划）。
- **执行主体：** 备考专家 / 命题思维教练Sub-Agent。
- **流程说明：**

  **\[P1]** 当请求类型为"知识点考法分析"时，备考专家必须调用TinyDB思维模型库与命题技术库，以历史数据支撑考法分析，而非仅依赖内置知识进行推断。

  **\[P2]** 当请求类型为"个性化复习规划"且用户已存在TinyDB学生学习记录时，备考专家应当优先基于个人历史数据进行精准诊断，而非给出通用建议。

  **\[P2]** 苏格拉底式引导对话完成后，备考专家应当将本次对话中产生的新考法洞察（如用户提出了一种未在库中记录的考法变体），标记为知识反哺候选项，纳入第五步迭代流程。

#### 6.1.7 学生能力点掌握度计算规则

**\[P1]** 学生学习数据库中各能力点掌握度（`mastery_by_ability_point`字段）的计算须遵循以下规则：

**基础算法：** 基于该学生在该能力点关联题目上的历史作答得分率，以最近3次有效作答记录为滑动窗口，采用加权平均计算，权重从最近到最远依次为3:2:1：

$$mastery = \frac{3 \cdot s_n + 2 \cdot s_{n-1} + 1 \cdot s_{n-2}}{6}$$

其中 $s_n$、$s_{n-1}$、$s_{n-2}$ 分别为最近三次作答中该能力点的归一化得分（取值范围0—1），以该次作答中涉及此能力点的得分点实际得分除以对应满分计算。

**数据不足处理：** 当该学生在该能力点的历史有效作答次数少于3次时，不输出数值掌握度，字段值标注为 `insufficient_data`，不参与"高危能力点"的排序计算，避免因样本不足产生误导性的伪精确数值。

**初始值规则：** 首次纳入学生档案时，所有能力点掌握度字段统一初始化为 `unassessed`（未评估），直至积累到足够的作答记录后由算法接管。

**更新时机：** 每次试题批阅专家完成批阅并写入诊断记录后，引擎自动触发对相关能力点掌握度的重新计算与更新，同步刷新 `knowledge_graph.last_updated` 时间戳。

### 6.2 TinyDB知识库存储规范

#### 6.2.1 TinyDB选型说明与适用边界

**选型理由**

TinyDB是一款轻量级的、纯Python实现的文档导向型数据库，以JSON文件为存储载体。选用TinyDB的核心理由如下：

- 与系统阶段相匹配：伏羲系统当前处于快速迭代的研究型项目阶段，数据模型需要频繁调整，TinyDB的Schema-free特性使得数据结构的修改无需数据库迁移操作。
- 零部署成本：无需安装和配置独立的数据库服务，整个数据库就是一组JSON文件，便于版本控制（可直接纳入Git管理）、备份与跨环境迁移。
- 与AI工作流自然集成：Sub-Agent的输出本质上是JSON结构化数据，TinyDB对Python原生数据结构的直接支持，使读写操作极为自然。

**适用边界说明**

**\[P1]** 以下场景在当前阶段必须被认识为TinyDB的使用边界限制，系统设计需规避在这些场景下对TinyDB产生强依赖：

- **并发写入：** TinyDB不支持高并发写操作。针对批量学生答案批阅场景（见第5章5.3.2节），系统采用串行批量写入策略（逐条顺序写入）作为标准规避方案。该方案在单次批阅40名学生以内的场景下经验证可接受，超出此规模时建议评估迁移至SQLite。
- **大规模数据量：** 当单个学科数据目录下的单表条目超过10,000条时，查询性能将显著下降。系统应在达到此规模前评估迁移至SQLite或其他数据库的必要性。
- **复杂关联查询：** TinyDB不支持跨表JOIN查询，复杂的关联数据需在应用层处理。

#### 6.2.2 多学科数据隔离机制

**\[P1]** 当系统同时存在多个学科的数据时，须采用以下两种互补的隔离机制确保学科数据不混淆：

**机制一：文件级隔离（主机制）**

每个学科的所有数据表存储于独立的学科子目录中，目录结构规范如下：

```
/db/
  /history/
    ability_points.json
    questions.json
    thinking_models.json
    question_techniques.json
    thinking_bottlenecks.json
    student_learning.json
    student_knowledge_graph.json
    feedback_candidates.json
  /math/
    ability_points.json
    questions.json
    ...
```

**机制二：字段级过滤（辅助机制）**

所有数据记录均包含 `subject` 字段，引擎在执行任何数据查询时须自动附加 `subject` 过滤条件，禁止跨学科数据的无意混用。即使在文件级隔离已生效的情况下，字段过滤也作为安全冗余保留。

**跨学科操作规范：** 若需执行跨学科的对比分析（如查询多学科共同的思维堵点类型分布），须通过引擎的专用跨学科查询接口执行，该接口将在返回数据中显式标注每条记录的 `subject` 来源，防止数据混淆。

#### 6.2.3 历史数据快照存储规范

**\[P1]** 所有支持版本追溯的数据表（能力点、思维模型、命题技术、思维堵点）在执行更新操作时，须遵循以下独立记录方案：

1. 不直接覆盖原记录
2. 将原记录的 `is_latest` 字段更新为 `false`，并写入 `archived_at` 当前时间戳
3. 创建新记录，`id` 字段保持不变，`version` 字段在原值基础上加1，`previous_version` 字段记录上一版本号，`is_latest` 设为 `true`，`archived_at` 设为 `null`，`change_summary` 填写本次变更说明
4. 所有常规查询操作默认仅返回 `is_latest == true` 的记录
5. 历史版本记录须通过显式指定 `include_history: true` 参数才能访问

**\[P1]** 引擎的统一写入接口须自动执行上述步骤，Sub-Agent不得自行管理版本字段。

#### 6.2.4 能力点数据库表结构设计

**\[P1]** 表名：`ability_points.json`（存储于对应学科子目录下）

**用途：** 存储所有提点与微题点的结构化记录，是整个系统的核心基础数据表。

**索引字段（应用层维护）：** `id`（唯一）、`subject`、`dimension`、`type`、`status`、`level`、`is_latest`。

**查询规范：**

```python
# 查看全部

# 按学科与维度查询微题点（默认仅返回最新版本）

         (where('dimension') == '时空观念') &
```

## 第7章 Sub-Agent间协同与交互需求

### 7.1 引擎与Sub-Agent的调度规范

#### 7.1.1 任务路由规则

**\[P1]** 伏羲引擎必须基于以下规则进行任务路由，将用户请求分配至正确的Sub-Agent：

| 用户请求特征 | 主责Sub-Agent | 可能协同的Sub-Agent |
|-------------|---------------|---------------------|
| 输入为《课程标准》文本 | 知形 | — |
| 输入为完整试题+官方解析，请求标注 | 能力点标注专家 | — |
| 输入为试题，请求教学解析 | 试题分析专家 | 能力点标注专家（查库） |
| 输入为学生答案，请求批阅 | 试题批阅专家 | 试题分析专家（生成评分标准） |
| 输入为知识点/试卷，请求备考建议 | 备考专家 | — |
| 输入为数据查询请求 | 引擎直接处理 | — |

当用户输入存在歧义（如一段文字既可能是课标节选也可能是题目材料），引擎须主动向用户确认任务类型，不得自行假设。当用户同时请求"试题解析"与"学生批阅"的合并任务时，引擎须自动识别并按串行方式处理：先完成试题分析专家的解析工作，再衔接批阅流程，整体作为一次任务调度。

#### 7.1.2 任务状态管理

**\[P1]** 对于跨越多个阶段的长任务（如单题标注的七阶段流程），引擎必须维护完整的任务状态，包含：当前所处阶段标识；各已完成阶段的产出数据缓存；任务整体的开始时间与预计完成阶段数。

**\[P2]** 任务状态应当支持断点续传，即在任务中途中断后，能够从上次完成的阶段继续执行，无需从头开始。

#### 7.1.3 质量门控执行规范

**\[P1]** 引擎必须在以下节点执行质量门控检查，检查不通过则阻止流程继续并返回具体失败原因：

- 单题标注流程中，阶段0完成后的原文完整性检查（验证题目原文、考查目标原文、解析原文均已呈现，降级模式下验证跳过说明已明确输出）
- 阶段C完成后的能力点格式合规性检查（验证所有编码格式符合规范）
- 数据写入前的必填字段完整性检查

### 7.2 Sub-Agent间任务传递与衔接规范

#### 7.2.1 试题分析专家→试题批阅专家的交接规范

**\[P1]** 试题分析专家在为试题批阅专家生成评分标准时，必须以以下完整结构的JSON格式输出：

```json
{
  "question_id": "string",
  "full_score": "integer",
  "scoring_points": [
    {
      "point_id": "string",
      "description": "string",
      "point_score": "integer",
      "ability_point_id": "string",
      "accepted_expressions": [
        {
          "expression": "string",
          "notes": "string"
        }
      ],
      "must_include_keywords": ["string"],
      "disqualifying_errors": ["string"]
    }
  ],
  "key_concepts": [
    {
      "concept": "string",
      "related_point_ids": ["string"]
    }
  ],
  "typical_error_warnings": [
    {
      "error_description": "string",
      "related_bottleneck_id": "string",
      "deduction_impact": "string"
    }
  ],
  "scoring_notes": "string",
  "generated_by": "string",
  "generated_at": "string",
  "prompt_version": "string"
}
```

**字段约束说明：** `question_id`、`full_score`、`scoring_points`、`generated_by`、`generated_at`、`prompt_version` 为必填字段；其余字段为可选字段，主观题中 `accepted_expressions` 须填写。引擎在将评分标准传递给试题批阅专家前，须自动验证 `full_score` 是否等于所有 `point_score` 之和，不等则拒绝传递并返回错误。

试题批阅专家必须严格以上述结构化评分标准作为批阅依据，不得使用非结构化的文字评分标准。

#### 7.2.2 能力点标注专家→聚合分析的数据交接规范

**\[P1]** 每道题目的标注任务完成并写入数据库后，引擎必须自动检查当前"学科+题型"组合下的新增标注计数是否触发聚合分析阈值，若触发则生成聚合分析任务并加入待执行队列。

#### 7.2.3 跨流程上下文共享规范

**\[P2]** 在同一会话上下文中，当用户先后发起"试题解析"和"学生批阅"请求时，引擎应当自动识别两个请求针对同一题目，并将前一请求中已生成的解析数据传递给批阅流程复用，避免重复分析。

### 7.3 共享知识资源访问规范

#### 7.3.1 读操作规范

**\[P1]** 所有Sub-Agent的读操作必须：

- 通过引擎统一接口执行，不直接调用TinyDB API（具体隔离机制详见附录A）
- 在读取前获取当前数据库版本号，并将版本号记录在本次分析的上下文中
- 当所需数据不存在时，返回明确的"数据不存在"信号，而非返回空结果后静默继续

#### 7.3.2 写操作规范

**\[P1]** 所有Sub-Agent的写操作必须：

- 经过引擎的格式合规性校验后方可执行
- 写入时自动附加创建时间戳、执行写入的Sub-Agent标识、当前数据库版本号及所使用的Prompt版本号
- 对于更新操作，须通过引擎的历史快照接口执行（详见6.2.3节），不得直接覆盖原记录

**\[P1]** 以下情况必须触发写操作失败并记录错误日志：

- 写入数据的 `id` 字段格式不符合编码规范
- 写入的关联ID在对应数据表的最新版本中不存在
- 必填字段缺失

### 7.4 异常处理与修正流程规范

#### 7.4.1 修正流程触发条件

**\[P1]** 以下任一情况下，引擎必须触发修正流程：

- Sub-Agent输出违反"原文强制呈现"原则（如阶段0未呈现题目原文直接输出分析结论）
- Sub-Agent输出的格式合规性检查未通过（如能力点编码格式错误）
- Sub-Agent输出通过格式检查，但触发语义质量异常（见7.4.4节定义）
- Sub-Agent输出不完整（如七阶段流程中某阶段未产出规定的输出结构）

#### 7.4.2 修正处理策略（三级梯度）

**\[P1]** 引擎须按以下三级梯度执行修正，从低到高依次升级：

**第一级：自动重试。** 适用场景：格式错误、原文呈现缺失等可被精确描述的规范性违反。引擎自动生成包含具体违反说明的修正Prompt，重新调用同一Sub-Agent的同一阶段，不中断整体流程。最大重试次数：2次。

**第二级：降级处理。** 触发条件：第一级重试达到上限仍未通过。处理方式：引擎保留已通过质量检查的部分输出，将未通过部分标记为"需补充"，继续后续工作流执行。降级处理的产出须整体附加 `degraded`: true 标注，用户可在收到最终报告时清晰看到降级说明。

**第三级：人工介入。** 触发条件：降级处理后输出仍不满足最低可用标准（如经七阶段流程后有效能力点识别数量为零）。处理方式：引擎暂停当前任务，向用户输出包含失败阶段、具体原因与已完成部分摘要的错误报告，等待用户指令（重新提供输入 / 跳过当前任务 / 手动补充结果）。

#### 7.4.3 重试次数上限与防无限循环

**\[P1]** 以下上限须严格执行：

- 单个质量检查节点：第一级自动重试最多2次
- 单次完整分析任务生命周期内：第一级修正介入总次数不超过3次

超过任意上限后，自动升级至下一梯度处理，不得继续在同一级别重试。

#### 7.4.4 语义质量异常定义

**\[P1]** 以下情况判定为语义质量异常，触发第一级重试（最终无法解决则升级至第三级人工介入）：

- 能力点的维度归属与该学科插件定义的维度范围不一致（如历史学科题目被标注为数学维度的能力点）
- 识别出的思维堵点类型不属于4.4.3节定义的四大核心堵点类型及其子类
- 知识形状赋值与题目设问动词完全不匹配（如包含"比较异同"的题目被赋值为"点形"）

## 第8章 质量保证机制需求

### 8.1 多轮自查与验证机制

#### 8.1.1 设计原则

多轮自查机制是伏羲系统区别于普通AI分析工具的核心质量保障手段。其设计哲学来源于一个核心认知：单次分析极易产生视角盲区与逻辑漏洞，通过强制性的多角度反复验证，才能逼近真正准确而非表面完整的分析结果。

#### 8.1.2 阶段A/B/C验证机制规范

**\[P1]** 在单题标注工作流中，以下三个验证阶段必须严格执行：

**阶段A的执行规范：**

- 引擎在调用Sub-Agent执行阶段A时，必须以独立的系统指令启动，显式指示Sub-Agent不得参照或引用阶段0的任何结论。该指令须明确列出阶段A允许访问的上下文范围：题目原文、官方答案、官方解析（如有）与能力点数据库，阶段0的产出数据不在此范围内。
- Sub-Agent必须在阶段A输出的开头以标准格式声明："本阶段分析独立进行，以下识别结论不基于阶段0的结果。"
- 阶段A的产出必须包含明确的"差异说明"，逐条解释与阶段0的一致项、新增项与存疑项。

**阶段B的执行规范：**

- 阶段B必须严格对照数据库编码格式执行格式化验证。
- 对每个能力点，必须明确说明其维度归属的依据，而非仅给出一个维度标签。
- 若某能力点的维度归属有争议（如可能属于多个维度），必须选择最主要维度并说明理由，而非任意选择或跳过。

**阶段C的执行规范：**

- 阶段C必须对阶段A中标注的所有"存疑项"给出明确裁决（保留/剔除/拆分/合并），不得遗留未处理的存疑项进入后续阶段。
- 阶段C的产出清单即为整个标注流程的最终权威结果，后续阶段不得再修改能力点列表。

#### 8.1.3 验证阶段的跳过限制

**\[P1]** 引擎必须强制执行以下规则：

在单题标注工作流中，任何单个验证阶段（A/B/C）均不得被跳过，即使题目看起来简单或与已有题目高度相似。若Sub-Agent在输出中未包含验证阶段的明确产出结构（含阶段声明语句），引擎须拒绝进入下一阶段并要求补充，此情况计入7.4.3节定义的修正介入次数统计。

### 8.2 自反性校验机制

#### 8.2.1 定义

自反性校验机制要求系统在产出任何方法论结论、数据库条目或分析规则时，必须将其自身作为检验对象，用同等严格的标准审视自身产出的质量，防止系统建立"对外有效、对内豁免"的双重标准。

#### 8.2.2 自反性校验的触发场景

**\[P1]** 以下场景必须触发自反性校验：

- **新思维模型提炼时：** 新定义的思维模型必须通过5.2.4节定义的"5道独立题目验证+三级裁决"才能正式入库。
- **新命题技术命名时：** 新提炼的命题技术名称与描述，必须能够通过以下测试——将描述交给未参与提炼过程的人（或Sub-Agent的全新会话），能否独立识别出同类型命题技术的新例子。若无法识别，则说明描述不够清晰，须修订。
- **能力点数据库版本升级时：** 新版本能力点数据库发布前，必须用至少10道已有标注题目进行回归验证，确认新版本对历史标注数据的解释能力未发生退化。

#### 8.2.3 自反性校验的输出要求

**\[P1]** 自反性校验的过程与结果必须记录在案，包含：验证所用的样本题目ID列表；验证通过/失败的具体情况；若有失败，失败原因的具体分析；最终裁决（正式入库/修订后重新验证/归档放弃）。

### 8.3 系统异常处置规范

#### 8.3.1 语义质量异常的定义与处置

语义质量异常指Sub-Agent的输出通过了格式合规性检查，但在内容层面出现了明显不合理的情况（如历史题目能力点被归入数学维度）。此类异常的识别标准与处置流程详见7.4.4节与7.4.2节。

#### 8.3.2 自反性验证持续失败的处置

**\[P1]** 当一个新思维模型在达到2轮修订上限（见5.2.4节）后仍未能通过验证（即处于"大部分失败"状态）时，须执行以下处置：

- 状态变更为"搁置（Suspended）"
- 所有修订历史与失败原因完整存入反哺候选池，标注"暂无法纳入"
- 搁置条目保留原始候选数据，不删除，供未来新证据出现时重新激活
- 引擎须通知用户该候选项已被搁置，并说明具体原因

#### 8.3.3 用户响应超时处置

**\[P2]** 当系统等待用户对反哺候选池进行评审确认时，若用户长期未响应，须按以下规则处理：

- 15天无响应：引擎生成提醒通知，列出待评审候选项清单。
- 30天无响应：引擎自动将待评审候选项状态变更为"暂存（Temp-archived）"，不影响正式数据库，相关分析任务可继续正常运行。
- 暂存状态的候选项可在任意时间由用户主动恢复评审状态，不设最终失效期。

### 8.4 Prompt版本管理规范

#### 8.4.1 Prompt版本号定义

**\[P1]** 每个Sub-Agent拥有独立的Prompt版本号，格式为：`[Sub-Agent标识]-Prompt-v[主版本].[次版本]`。例如：`annotation_expert-Prompt-v1.2`。

**版本号递增规则：** 主版本号在影响能力点识别逻辑、标注阶段行为或输出格式规范的重大修改时递增（如阶段A的独立分析指令修改）；次版本号在措辞调整、示例更新、提示语优化等不影响核心识别逻辑的修改时递增。

#### 8.4.2 Prompt版本的数据追溯要求

**\[P1]** 所有写入TinyDB数据库的标注记录须附带生成时所使用的Sub-Agent Prompt版本号（对应各数据表的 `annotated_by_prompt_version` 或 `created_by_prompt_version` 字段）。引擎在执行写入操作时须自动读取当前激活的Prompt版本号并附加至记录中，不依赖Sub-Agent自行填写。

#### 8.4.3 主版本升级的兼容性评估

**\[P1]** 当任一Sub-Agent的Prompt发生主版本升级时，须在新版本正式启用前完成以下兼容性评估：

- 随机抽取不少于10道已有标注题目，分别使用新旧版本Prompt各执行一次分析
- 比较新旧版本在能力点识别结果、堵点归类、知识形状赋值上的差异，计算各维度一致率
- 若任一维度一致率低于80%，须生成详细差异报告，由用户决定是否对受新版本影响的历史标注数据执行批量重新标注
- 无论是否触发重新标注，兼容性评估报告须存档，新版本正式启用时间须记录于引擎配置日志

## 第9章 系统动态进化需求

### 9.1 知识反哺与迭代机制

#### 9.1.1 反哺数据的来源与触发

**\[P1]** 系统必须在以下场景自动识别并标记知识反哺候选数据：

- 能力点标注专家在阶段B执行"维度定位与能力点再匹配"时，发现数据库中没有对应编码的认知操作（标记为"新能力点候选"）
- 试题分析专家在分析过程中识别出数据库未覆盖的命题技术（标记为"新命题技术候选"）
- 试题批阅专家在诊断过程中识别出数据库未覆盖的思维堵点类型（标记为"新堵点候选"）
- 备考专家在苏格拉底式对话中与用户共同发现的新考法变体（标记为"新考法候选"）

**\[P2]** 系统应当维护一张"反哺候选池"数据表（`feedback_candidates.json`，存储于对应学科子目录下），自动收集上述标记数据，供定期评审使用。

#### 9.1.2 反哺评审流程

**\[P2]** 反哺候选池的评审应当遵循以下流程：

- 候选项积累达到5条，或用户主动发起评审时，引擎生成评审报告，列出所有候选项及其来源证据
- 用户对每条候选项做出"接受/修改后接受/拒绝"的裁决
- 接受的候选项进入数据库版本升级流程（详见5.2.5节）
- 拒绝的候选项附上拒绝理由存档，防止同类候选项重复出现
- 超时未响应的候选项按8.3.3节规则处理

### 9.2 新能力点 / 模型 / 堵点的发现与纳入流程

**\[P1]** 以下是新知识单元从"候选"到"正式入库"的完整状态流转规范：

**状态一：候选（Candidate）：** 由Sub-Agent自动标记产生，尚未经过人工评审。此状态的数据仅存储于反哺候选池，不影响正式数据库的查询结果。

**状态二：待验证（Pending Validation）：** 用户初步接受候选项后进入此状态。系统自动使用现有题目数据集对候选项进行自反性校验，生成验证报告供用户参考。

**状态三：正式（Active）：** 通过自反性校验，用户确认后正式写入数据库，状态更新为Active，纳入所有查询操作的覆盖范围。

**状态四：搁置（Suspended）：** 候选项验证多轮失败，按8.3.2节规则处置，暂不入库但保留数据。

**状态五：已归档（Archived）：** 因数据库版本升级导致的替换、合并或废弃条目，进入已归档状态（`is_latest` 设为 false）。归档数据保留但不参与常规查询，历史引用保持可追溯性。

### 9.3 学科插件扩展与新增规范

**\[P1]** 新增学科插件的正式发布必须满足以下最低标准：

- 能力点数据库组件已完成知形的完整六步拆解流程，包括满足4.1.3节Step 6定义的收敛标准或达到5轮迭代上限
- 已完成不少于50道真题的Step 3验证标注（此50道为验证标注总量；其中不少于20道须经人工审核并纳入标注示例库组件，两者为包含关系）
- 标注示例库已包含不少于20道经人工审核的典型案例，须由学科领域专家（一线教师或命题研究者）完成审核
- 错误类型库已覆盖至少10种该学科常见思维堵点类型
- 插件版本号已按规范登记，并通过引擎的格式合规性检查

**\[P2]** 插件扩展应当支持"同学科多地区版本"并存，通过在插件ID中附加地区标识（如 `history_national_a` 与 `history_beijing`）进行区分，引擎在任务启动时根据用户指定或默认配置选择激活的插件版本。

**\[P3]** 系统可以提供"插件差异比较"功能，当用户切换同学科不同地区版本时，自动生成两个版本在能力点覆盖范围、频率分布与命题技术偏好上的差异报告。

## 第10章 核心概念术语表（Glossary）

| 术语 | 定义 |
|------|------|
| **伏羲引擎（Fuxi Engine）** | 整个系统的统一核心与调度中枢，不包含任何具体学科知识，负责方法论执行监督、Sub-Agent调度、共享知识资源管理与质量门控。其工程实现形态为封装了所有数据库操作的Python Orchestrator模块，详见附录A。 |
| **Sub-Agent** | 受伏羲引擎统一管理的五个专项AI角色，分别为知形、能力点标注专家、试题分析专家、试题批阅专家、备考专家。每个Sub-Agent拥有明确的功能边界与行为规范，在工程层面对应配置了特定System Prompt的LLM会话实例。 |
| **学科插件（Discipline Plugin）** | 可插拔的学科专业知识包，包含能力点数据库、标注示例库与错误类型库三个标准组件。切换学科只需替换插件，引擎与Sub-Agent逻辑保持不变。 |
| **能力点（Ability Point）** | 系统分析体系的基本单元总称，泛指所有被拆解出来的、描述学生认知操作的结构化单元，涵盖提点与微提点两个层级。 |
| **提点（Topic Point）** | 能力点的宏观层级，直接从课标"学业质量水平"原文中提取的一个完整的、独立的能力动作描述单元。 |
| **微题点（Micro-Topic Point）** | 能力点的微观层级，由提点进一步拆解而来，判断标准是"单独拿出来能够独立支撑一道考试题目的设计"，是系统中可直接用于命题和精准测量的原子单位。 |
| **思维模型（Thinking Model）** | 由多个微题点按特定逻辑顺序组合而成的、可复用的认知流程。通过对大量试题的能力点序列进行模式识别后提炼，需经过5道独立题目验证的三级裁决机制方可正式入库。 |
| **思维堵点（Thinking Bottleneck）** | 学生从"看懂题目"到"选对答案"的思维过程中，在某个关键环节被卡住或发生断裂的现象。分为四大核心堵点类型（多要素综合判断堵点、知识迁移堵点、层次抽象堵点、逻辑链条构建堵点），每种类型均有操作性区分标准（详见4.4.3节），以及基于知识形状转换的六类卡点。 |
| **命题技术（Question-setting Technique）** | 命题人为制造思维堵点、区分学生层次而采用的有意设计手段。命题技术与思维堵点之间存在对应关系：堵点是学生视角的体验，命题技术是命题人视角的设计行为。 |
| **知识形状（Knowledge Shape）** | 同一知识点在不同设问方式下被激活的六种不同认知结构形态，分别为点（●提取）、网（◈整合）、链（→排序）、层（▽穿透）、镜（◇映射）、锥（△压缩）。知识形状由能力点标注专家在阶段4通过识别规则自动赋值，用于指导批阅专家的读想双维归因。 |
| **材料处理五步链（Five-Step Information Processing Chain）** | 针对"读"的维度的思维操作框架，描述有效阅读题目材料的五个环节：定位→解码→筛选→提纯→隐含推断。每个环节均有操作性定义与典型错误识别标准（详见4.4.3节），用于试题批阅专家执行读维度断裂位置的精确归因。 |
| **认知对称性（Cognitive Symmetry）** | 系统的核心设计哲学之一，即"解析即命题"。深度解析一道题所需的认知能力与设计这道题所需的认知能力，在本质上是同一能力的双向应用。 |
| **知识反哺（Knowledge Feedback）** | 系统动态进化机制的核心，指在教学应用流程中新发现的知识单元（新能力点、新思维模型、新命题技术等），经过评审验证后被纳入正式数据库，从而使系统持续迭代演化的闭环机制。 |
| **四元区分法（Four-Element Analysis）** | 对命题目标进行结构化拆解的标准方法，从"做什么（核心认知动作）"、"怎么做（方式路径）"、"用什么（知识资源）"、"到什么程度（能力水平）"四个维度解析官方考查目标原文。 |
| **七问法（Seven-Question Method）** | 知形用于深度解读《课程标准》文本的核心方法论，通过"它说了什么→为什么这么说→为什么放在这里→和谁一起说→没说什么→反例是什么→最终指向什么"七步追问，挖掘文本的深层认知秩序。 |
| **自反性校验（Reflexive Verification）** | 系统质量保证机制之一，要求系统用同等严格的标准审视自身产出的知识与结论，防止双重标准。新思维模型须通过5道独立题目验证的三级裁决方可入库。 |
| **降级模式（Degraded Mode）** | 当官方试题解析缺失时，能力点标注专家以受限方式运行的工作状态。降级模式下产出须标注 `analysis_quality: reduced`，存入待补充队列而非正式数据库。 |
| **异常修正流程（Anomaly Correction Process）** | 引擎在Sub-Agent输出不符合质量规范时触发的三级梯度处置机制：第一级自动重试（最多2次）→ 第二级降级处理 → 第三级人工介入。 |
| **历史快照（Historical Snapshot）** | 数据记录版本管理机制，通过独立记录方案（新记录 `is_latest: true`，旧记录 `is_latest: false` 并标记 `archived_at`）保留所有历史版本，实现数据的完整可追溯性。 |
| **Prompt版本号（Prompt Version）** | 每个Sub-Agent的Prompt配置版本标识，格式为 `[Sub-Agent标识]-Prompt-v[主版本].[次版本]`，须附加至所有该Sub-Agent生成的数据库记录中，用于追溯数据生成环境。 |
| **L2专线** | 单题标注报告中的精简摘要板块，从完整分析报告中单独提取命题技术、思维堵点与本质规律等核心发现，供快速查阅使用。 |

## 附录A 引擎实现架构说明

### A.1 附录定位

本附录为引擎在工程实现层面的补充说明，解释"Sub-Agent不得绕过引擎直接操作数据库"这一架构原则的具体工程实现形态。本附录不构成强制性功能需求，而是为开发人员提供一种符合本文档架构意图的参考实现方案。

### A.2 引擎的工程实现形态

在工程实现层面，"伏羲引擎"对应Python代码库中的一个Orchestrator模块（协调器），其核心职责通过以下组件实现：

- **Tool Function Layer（工具函数封装层）：** 将所有TinyDB数据库操作封装为标准Python函数（如 `read_ability_points()`、`write_question_annotation()`），这些函数构成引擎对外暴露给Sub-Agent的唯一合法数据访问接口。
- **Quality Gate Module（质量门控模块）：** 在工具函数内部实现格式合规性验证、必填字段完整性检查和语义异常检测，在数据读写发生前后自动执行。
- **Task State Manager（任务状态管理器）：** 维护跨阶段的任务上下文，记录当前阶段、各阶段缓存数据与修正介入次数。
- **Version Manager（版本管理器）：** 自动处理历史快照的创建、`is_latest`字段的维护以及Prompt版本号的自动附加。

### A.3 Sub-Agent的技术实现形态

Sub-Agent在工程实现层面对应配置了特定System Prompt的LLM会话实例。Sub-Agent本身不持有任何TinyDB文件路径信息或数据库连接字符串；所有需要数据读写的操作，均须通过LLM的Function Calling机制调用引擎工具函数完成。

Sub-Agent在其Prompt配置中仅声明可调用的工具函数名称与参数签名，不包含任何直接数据库访问的能力。

### A.4 数据访问的合法路径

Sub-Agent访问数据库的唯一合法路径为：

```
LLM Sub-Agent
→ Function Call（调用工具函数名称）
→ 引擎 Orchestrator（质量门控 + 版本管理）
→ TinyDB API
→ JSON 文件
```

任何绕过引擎Orchestrator直接访问TinyDB API或JSON文件的操作，均视为违反架构规范。

### A.5 阶段A独立分析的技术实现

4.2.3节要求阶段A以独立的分析指令启动，不得参照阶段0结论。在工程实现层面，此要求通过以下方式实现：引擎在启动阶段A时，向LLM发送一个新的System Prompt调用，该调用中显式包含"不得引用阶段0结论"的指令，且不在此次调用的上下文窗口中传入阶段0的产出数据。阶段0的产出数据由引擎的Task State Manager单独缓存，仅在阶段A完成后用于比对分析，不参与阶段A的LLM上下文构建。
