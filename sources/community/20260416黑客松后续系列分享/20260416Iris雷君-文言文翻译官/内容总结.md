# 文言文翻译官：引导式分步拆解

> 分享日期：2026年4月16日
> 分享人：Iris老师（语文）、雷君老师（技术背景、AI教育竞赛服务商）
> 作品：文言文翻译官——10步引导式文言文拆解学习网页（水墨风+API调用文生图）

---

这一组分享的主线是两条：前半场Iris老师讲作品设计，后半场雷君老师讲后端部署这件事情老师到底该怎么做。整场分享的重点其实不是作品本身，而是**前端HTML到底够不够用、要不要接入API和数据库、老师做出来的产品怎么分发给学生**这些更实际的问题。

**作品设计：把文言文拆成10步，用"心流"对抗"太散了"**

Iris老师是语文老师出身，她对文言文教学的痛点抓得很准。学生望而生畏主要是因为**文言文和现代汉语差异大**（通假字、一词多义、特殊句式），**知识点太散**（她举例自己高中时老师让买词典查，一开始会用、后来就不用了——效率太低），**遗忘率高**，以及**老师负担重**。

她和雷君做的产品不是"帮学生一次性翻译完"，而是把文言文拆成**10个步骤**，每一步都必须学生参与完成才能点下一步——这是整个产品的核心约束。她反复提到"心流"这个概念：把所有分散的查词、翻译、背景理解动作集成在一个页面里，让学生不跳出来，一步步走到终点。

10个功能依次是：原文呈现（古风竖版/横版切换）、通假字拆解、古今异义、一词多义、词类活用、句式（倒装/被动/省略/判断）、虚词、作者背景与时代背景、情感与主旨探索（填空选择题形式）、最后导出清单笔记（分"必背/易错/高频"）。最有趣的一个特别功能是**接入了即梦API做文生图**——学生鼠标点中一句话，就能即时生成一张水墨风意境图。这个功能是把"理解"直接变成"画面"。

Iris在开发过程中踩过一个坑值得分享：第一次给Cursor一次性提了太多功能（点击词要读音、词性、释意全都要），Cursor跑不出来。她的教训是**把需求拆小，核心功能先跑通，再逐步加**——先砍掉了读音和词性，先把结构跑起来。

**技术方案：Cursor做前端、Cloud Code做后端、JSON存数据库**

雷君老师讲了他们的实际开发链路：

1. **先做思维导图**——分析文言文翻译官要做什么
2. **让豆包补强需求**
3. **多轮对话讨论需求**
4. **用Cursor生成前端代码**（原因是当天Claude Code有问题，所以他们先用Cursor跑的第一版）
5. **用Cloud Code接入即梦API和在线数据库**
6. **每篇文言文生成一个JSON文件**，存到阿里云文档

数据库的设计是这样：老师自行上传一篇文章 → 系统调用大模型（比如DeepSeek）把这篇文章解析成一个JSON串（包含所有知识点标注） → 存入数据库 → 前端就能读取了。雷君说初中阶段文言文一共也就40来篇，他们想一次性传完，但也保留"老师自行上传"的入口——课外阅读的需求还是得满足。

TeacherYo在这里追问了一个关键问题："**如果老师上传一篇不知道哪来的篇目，那对这篇文章的拆解讲解，是不是纯靠模型能力？**"雷君确认是的——他们的提示词是按初中/高中大纲设计的，只要是普通文言文，大模型是能处理的。这其实是Vibe Coding产品的一个通用问题：**预制内容靠你，泛化能力靠模型。**

**真正的硬核：后端部署这件事**

分享的后半段雷君讲的是"老师做AI产品的终极门槛"——后端部署。他先解释了痛点：Cursor之类生成的代码大部分是前端HTML，如果你想调用API（比如即梦的图片生成）、想保存用户数据、想让学生登录留痕迹，就必须要有后端——而后端部署涉及服务器、上传、维护，对一般老师来说太难了。FastAPI能帮你写后端代码，但你依然得自己部署到服务器上。

他给出的推荐方案是：**扣子（Coze）**。扣子解决的是老师"不想碰服务器"这个刚需——它有大模型调用、生图、语音识别、数据库、一键部署，你做完了点一下部署，它直接给你一个网址，你把网址分享出去学生就能用。扣子个人进阶版一个月9.9元，3万积分基本够单个老师带一个班用。

雷君本人正在给一家幼儿园做智能阅读系统——学校入口做完整阅读、精读、互动问答；后台做班级管理、学生管理、绘本管理。他只需要把功能需求告诉扣子，扣子就调用自己的大模型和Supabase在线数据库把整个网页搭起来。他的观点很直接：**对老师来说，能做出"有后端的应用"就已经是上限了，智能体/Agent涉及的工作流编排范围太大，先别惦记。**

**一个被多次提到的核心问题：token的钱谁出？**

TeacherYo顺势抛出了这个问题——"大家做了部署之后，也希望老师能体验到Agent的功能，但这个API的钱谁出，token到底谁来付，其实就会是一个很大的问题。" 雷君的回答很实在：**老师带自己几个学生用，可控；扣子充点积分就够。真要做商用的大分发，那就必须走正规服务器部署了。** 这个问题是目前老师自制AI产品无法规模化的核心障碍。

**分享最后的一个认知转向**

TeacherYo的总结抓得很准："**我整体感觉会觉得接下来大家都会更倾向于去做自己的Agent，还是要回到Agent这种形式上面，可能大家会觉得更加实用。**" 雷君补充："飞翔老师目前交付还是HTML这种形式，没有后端的话会有很多问题——一个数据都没办法保存，学生提交一个成绩都没办法提交。"

这一组分享的真正价值，在于把整个社群老师的注意力从"做一个HTML"拉回到了"做一个真正能留存数据、能让学生用的应用"上来。HTML是过渡，应用化/Agent化才是方向。
