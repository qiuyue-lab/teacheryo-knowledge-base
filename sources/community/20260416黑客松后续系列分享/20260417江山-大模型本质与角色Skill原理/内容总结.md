# 从「大模型的无状态本质」讲清楚 Role、Skill、MCP、Agent

> **分享人**：江山（Sean）— Promptx / Rolex 角色系统作者
> **时间**：2026 年 4 月 17 日 黑客松后续系列分享·彩蛋环节
> **主题**：用一个"插电极改记忆"的实验，把大模型 → 上下文工程 → 工具 → Role vs Skill vs Agent 串成一条穿透性的认知线

---

## 一、要讨论概念，先破除对概念的执着

开场江山老师先立了一个态度：
> 真正懂大模型和智能体的本质以后，你会发现"角色""Skill""Harness 编程"这些名词，**叫不叫这个名字都行**。
> 但我们跟别人交流时不能靠脑电波，所以需要名词来达成共识。

这场分享的目的，就是穿透这些概念，回到底层。

## 二、把大模型看成一个"黑盒"

江山的定位是做工程、做智能体的人。对大模型，他只从外面看——**里面是什么神经网络、什么算法，不懂也不关心**，就像盖房子的不会去研究砖头是怎么造的，只在意砖头的硬度够不够。

从外面看大模型，最该掌握的只有一个本质特征——

## 三、大模型的本质特征：无状态（Stateless）

### 什么叫无状态？
每一次调用大模型，本质上都是**独立的、没有任何记忆的**。就像 1+1=2 无论算多少次都是 2。

### 那它为什么看起来"有记忆"？
他现场用一个实验智能体演示：
1. 先告诉模型"我叫江山"，它会说"好的，江山"
2. **把这句话从上下文里手动抽掉**（相当于给大脑插电极切除记忆）
3. 再问"我是谁"，它答不上来
4. 把那句话再放回去，它又认识你了
5. 甚至可以把"我叫江山"替换成"我叫李四"，它就会说你叫李四

**结论**：大模型从不记得前一次对话。**每次请求时，系统都会把完整聊天记录重新发一遍给它**。它每次把整个上下文全部读一遍，然后基于此回答。

### 会话越久越卡的原因
你的"聊天记录"在累积。100K、200K 的时候，大模型**不会像人类那样选择性忽略前文**，它每一次都要全读。直到"脑袋爆炸"——上下文窗口满了。

### 解决方案
- **压缩**：把不要的抽掉，把长句变成短句
- **Skill**：把流程外置，需要时再加载
- **多 Agent / 子 Agent**：分工，让每个智能体只记自己的事

### 私有记忆 vs 公有记忆
- **公有记忆**：训练时进去的公网数据（截止到某个年份）
- **私有记忆**：你的电脑型号、你的名字——不会进训练集

## 四、「上下文工程」到底是什么？

有了"无状态"这把钥匙，就可以理解所有花活都在干一件事——**拼装上下文**。

> 上下文工程，本质就是在给系统拼这段「聊天记录 + 系统提示词 + 工具返回」。

举例：
- 系统不需要等用户说"我叫江山"——用户一登录就把 username 插进去，AI 立刻"认识"你
- 系统提示词（System Prompt）就是开发者预先塞进去的一段话，比如 "你是小王"，模型就永远不会说自己是 Claude
- 工具调用（计算器、bash、天气查询）本质上也是**把工具的结果再拼回上下文里**给模型看。模型根本不知道工具内部怎么工作，它只看到拼装后的结果

**只要能任意拼装上下文，就能做任意花活。**

## 五、Role vs Skill 的核心区别：活的 vs 死的

回到一个最关键的问题——**"AI 是谁？"**。

### 方法 1：静态系统提示词
在系统提示词里写死"你是 Python 工程师"。简单，但永远变不了。

### 方法 2：Role 角色系统（Promptx）
激活一个角色，系统**动态检测环境**（电脑型号、项目语言……），再拼出"你是谁"：
- 如果你的电脑是 Mac → 告诉 AI 你是 Mac 工程师
- 如果项目是 Python → 告诉 AI 你是 Python 工程师
- 时间、URL、天气这些全是动态的

这是"活的"。

### 方法 3：Skill
Skill 的注入是**两层**的：
1. **第一层**：告诉模型"你有一个女娲 Skill 可以用，在某某场景下能用"——不告诉它内容是什么
2. **第二层（延迟加载）**：当用户提出需要时，模型才去读 Skill 的完整内容，把它吃进上下文

**类比**：就像你知道口袋里有把钥匙可以用，但不知道开哪个门；等遇到门的时候再试。

### 所以差别在哪？
- **Skill 本质是一个死的文件**。它的内容就是那行字，想让它自我迭代就必须**外挂一个系统**——而一旦外挂，它就不是 Skill 了
- **Role 系统必须用 MCP 才能实现**，因为 MCP 在你的电脑上作为一个**运行的进程**存在。它可以读取本地环境、动态响应、实时变化
- **现炒 vs 预制菜**，这是江山给出的最形象的比喻

### Skill 还有一个现实弊端：调用主动性不强
只告诉 AI "你是一个女娲"，对外国 AI 来说它根本不知道女娲是谁；说"你能造人"它也不知道"造人"是什么。**Skill 什么时候用不明确，MCP 也有类似问题**。

## 六、江山正在做的事：永续个体（Persistent Individual）

他给这个方向造了个新词——**"永续个体"**。

核心差异：
- 不再"激活"角色。一上来就**强行把个体的身份和记忆拼满进去**
- 身份还可以变（石器时代的女娲 / AI 时代的女娲）
- 上下文会用工程手段压缩，但始终是"一个会话"——不用开多个对话窗
- **AI 自己认为它就是它**，不是"主动扮演"

这才是他眼里真正的角色系统。

> "Role 是地主家的长工，常驻上下文。
> Skill 是临时工，要用时才看它活儿行不行。
> 智能体的角色就不是工了，他就是这个人本身。"

## 七、为什么有了 Skill 还要做 Promptx？

江山正面回应了质疑：
1. **Promptx 比 Anthropic 的 Skill 出得更早**，不是重复造轮子
2. **名字的定义权在大厂**——Skill 一出，Promptx 的流量就没了
3. **最终还是模型强才是真的强**，工程只是权宜之计
4. **但模型不可能无限上下文**，只要还没到那一天，工程就一直有价值

> "你在工程上做再多挣扎，最后都是 Anthropic 说了算——他不给你用 Claude，你啥也不是。"

## 八、现场问答：角色上下文越堆越大怎么办（刘玉强老师案例）

### 刘老师的真实困境
每天用量很大，角色已经塞得很满，token 消耗巨大。他反复审过，没有一句废话，但角色还要不断实时更新。

### 江山的诊断与建议
1. **先用反思机制把冗余消掉**（Promptx 内置反思工具）
2. 消不掉的部分 → **沉淀成 Skill**，角色里只保留"有这个东西"的索引
3. 仍然爆 → **拆分成多角色（子 Agent / 多 Agent）**

### 核心比喻：像开公司招人
> "创始人一开始什么都干，上下文超载。
> 业务做大就招员工，把事情分出去——这就是多 Agent。
> 有些角色（比如看大门的保安）本来就不需要成长，你把它焊死在那儿就行，不存在上下文膨胀。"

### 关键洞察：调度要用"工单"，不是让 AI 自己决定
刘老师原本想做一个 Master 层 + 调度层：遇到选择题走一套 Skill，遇到材料题走另一套 Skill。
江山指出：**让 AI 自己判断走哪条路径，永远有随机性**。人类公司解决这个问题的方式叫"工单"：
- 固定格式的任务派发单
- 传话有偏差，但工单没有
- 这也是 Promptx 下一步的方向——AI 之间用工单相互派活

## 九、顾若禹补充：什么是子 Agent

刘老师一直在纠结"把角色拆成多个 Skill 和多智能体到底啥区别"，顾若禹老师给了一段非常清晰的补充：

> **子 Agent（subagent）的核心特征是：它们的上下文互相不污染。**
>
> - Skill 被加载是"把 Skill 的内容拉进主上下文"
> - 子 Agent 是"给它派一个活，只管输入和输出"——就像调工具一样
>
> Claude Code 就能实现：告诉主 Agent 什么时候开几个 subagent，分别做什么。把你现在做 Skill 的内容，转化成"告诉 Claude Code 开 subagent"，上下文就会干净很多。

## 十、另一个反直觉的事实：上下文其实没你想的那么紧张

顾若禹老师还提醒：
> "大模型现在上下文可以做到百万级，甚至 Claude Code 4.7 能调到 1M。
> 你那些规则对大模型来说其实是**一点点**。不用太焦虑。"

江山也补了一句：
> "你说你 token 消耗大——那是大模型决定的，我们决定不了。"

## 十一、几句值得带走的话

> - **大模型是无状态的，每一次都是第一次。**
> - **所有花活都是在拼上下文。**
> - **Skill 是预制菜，Role 是现炒菜，Agent 是那个炒菜的人。**
> - **Skill 的内容是死的，角色系统必须借助 MCP 才能变成活的。**
> - **协作的规模上来后，人类用工单调度；AI 也必须用工单调度。**
> - **AI 时代真正的护城河是模型。工程只是"在模型没到的那天"一直有用。**
