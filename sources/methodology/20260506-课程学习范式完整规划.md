## 二、核心理念：学习系统，不是课程视频

### 我们在做什么

我们在做的事情不是"把视频换成网页"，而是**重新定义什么叫课程**。

| 传统范式 | 我们的范式 |
|---------|-----------|
| 课程 = 老师讲的视频 | 课程 = 一段被设计过的学习经历 |
| 学习 = 看视频/听讲 | 学习 = 走完一条精心设计的路径 |
| 老师的价值 = 讲得好 | 老师的价值 = 有真实经验和洞察 |
| 课程质量 = 老师表达能力 × 制作能力 | 课程质量 = 学习设计框架 × 素材质量 |
| 学完想深入 → 没人可问 | 学完想深入 → 课程教师agent随时交流 |
| 信息传递为核心 | 认知建构为核心 |

### 为什么这个方向是对的

1. **信息传递的价值已经被AI打到地板。** 任何分享录音，AI三分钟总结完。如果课程核心价值是"帮你把知识整理清楚"，那跟AI竞争不了。

2. **理解无法被直接传递，只能被自己建构。** 视频的问题不是"视频"这个介质，而是它背后的假设有问题——假设"我讲清楚了你就会了"。学习系统的假设是"你必须自己走过那条路"。

3. **门槛降低释放的是创造力。** 过去做一门好课需要老师既有内容、又有表达、又有制作能力。我们把后两者用系统解决，让只要"有真东西"的老师都能产出高质量的学习体验。

## 三、产品形态：三层架构

### 第一层：HTML交互式学习系统（主学习路径）

**定位：** 承载完整的学习路径，是学生学习的主体验。

**特征：**
- 不是教案，不是讲义，是"一段被设计过的经历"
- 交互式：每个模块有输入、有触发、有隐藏内容展开
- 认知递进：模块之间有严格的认知递进关系，不是知识点堆叠
- 老师以"先行者"身份嵌入：关键节点出现老师的真实经历和原话
- 确定性强：路径经过精心设计，每个学习者走的核心路径是一致的
- 纯前端：不依赖后端/API，打开即学，离线可用

**核心设计原则（已验证）：**
- 先体验，再讲概念
- 学习者的真实问题贯穿全程
- 老师的素材是"参照"不是"教材"
- 最反直觉的洞察放在实操之后
- 框架工具从案例中自然浮现

**视频的位置：** 视频只是备份和原材料。严格意义上，学生跟着学习系统走完，就不需要看视频。视频是"课程的素材来源"，不是"课程本身"。

### 第二层：课程教师agent（浮窗交互层）

**定位：** 学习系统的辅助延展，处理HTML覆盖不到的个性化需求。

**特征：**
- 从这节课老师的原始表达中"捏"出来的临时教师分身
- 灌入课程内容作为上下文 + 大模型能力
- 以浮窗形式嵌入，学生随时可以唤出
- 它是"非完全体"——只知道这一节课的内容，不是老师的全部

**与学习系统的关系：**
- 学习系统 = 主路径（确定性、设计精度）
- Agent = 辅助路径（灵活性、个性化）
- 学生跟着学习系统走是核心体验；想交流、有疑问时唤出agent

**agent的定位边界：**
- 能做：这节课内容范围内的答疑、延展讨论、换角度解释
- 不做：超出这节课范围的问题 → 引导用户预约咨询
- 风格：用这节课老师的表达风格和语气，保持一致性

**技术实现要点：**
- agent浮窗加在外壳层（不是iframe内），覆盖整个页面
- agent状态跨模块持续
- 外壳层传递当前学习进度给agent（"学生正在学模块3"），让回答更有针对性
- 课程转写先压缩为结构化知识库（关键观点+案例+金句），检索相关段落作为context，不全量灌入

### 第三层：深度咨询入口（人工层）

**定位：** agent覆盖不了的、需要真人判断的问题，引导付费咨询。

**商业逻辑：**
```
免费/低价：HTML学习系统（获客、体验）
    ↓
中间层：agent交互（延展、留存）
    ↓
高价值：1对1咨询（变现、深度服务）
```

**关键设计：** agent在遇到超出范围的问题时，主动引导："这个问题比较深，建议你预约一次和老师的1对1交流。"

## 四、生产侧：角色+Skill驱动的课程生产

### 核心工具：TeacherYo课程设计师（角色产品）

**定位：** 这不是平台后台的隐形基础设施，而是一个**有品牌、可感知、未来可收费的角色产品**。

**为什么要让老师"有感知"：**

1. **符合平台定位** — 我们卖的是角色平台。自己的核心生产力如果藏起来当黑箱，就在用行动否定产品理念。

2. **最好的产品演示** — 老师用了之后发现"一个小时的分享录音丢给这个角色，它帮我设计了完整的学习系统"——这比任何营销都有说服力。

3. **自然形成第二条收入线** — 学生付费学习（第一条线）+ 老师付费使用课程设计角色（第二条线）。

4. **让老师变成分发渠道** — 老师用角色生产课程→课程上架→老师拉学生→学生体验好→有些学生也想做课程→也来用角色→飞轮。

### 角色的能力构成

```
TeacherYo 课程设计师
├── 核心方法论：学习系统设计原则（从实践中提炼）
├── Skill 1：素材分析 — 从转写/录音中提取认知转变
├── Skill 2：学习路径设计 — 按认知递进排列，设计经历路径
├── Skill 3：HTML学习系统生成 — 基于模板框架产出交互式网页
├── Skill 4：课程教师agent定义 — 从素材中提取老师风格，生成agent角色设定
├── Skill 5：审美呈现 — 视觉风格、卡片类型、信息层次的设计标准
└── Skill 6：质量审核 — 检查认知递进是否成立、信息量是否合理
```

### 生产流程（老师视角）

```
老师被邀请，获得"创作者"身份
    ↓
登录创作者后台，看到：「课程设计师·TeacherYo」已就绪
    ↓
上传素材（两项必填）：
  ① 直播回放链接（主入口，系统自动获取转写）
  ② 补充素材（课件/文档/聊天记录/幕后思考等）
    ↓
角色开始工作：
  "我读完了你这一个小时的分享。我识别到了4个核心认知转变：
   1. 从A到B
   2. 从C到D
   3. ...
   你觉得这个排序对吗？有没有我遗漏的重要洞察？"
    ↓
老师确认/修改排序和重点
    ↓
角色继续：生成6模块学习路径方案
    ↓
老师预览学习路径，确认每个模块的核心目标和素材嵌入点
    ↓
角色产出：
├── HTML交互式学习系统
├── 课程教师agent角色定义
└── 课程元信息（标题、简介、标签、模块结构）
    ↓
老师预览完整学习系统，微调文案和细节
    ↓
提交发布
```

### 上传权限：邀请制

**为什么必须是邀请制：**

1. **质量门槛** — 不是所有人的内容都值得变成学习系统。邀请 = 你判断过"他有真东西"。
2. **平台调性** — 每一门课都经过筛选，这本身就是品牌价值。避免变成无门槛UGC平台。
3. **生产质量** — 新老师第一次用需要引导，邀请制让你可以控制节奏和质量。

**权限设计：**
- 你邀请 → 老师获得创作者身份
- 创作者可以：上传素材、与课程设计师角色协作、预览和微调、提交发布
- 你保留：终审权（至少在早期）

## 六、实现路径：三个阶段

### Phase 1：手动打磨，验证模型（现在）

**目标：** 验证"学习系统"这种形态是否真的比传统课程更能让学习者产生认知转变。

**具体动作：**
- [x] 完成荻荻课程的学习系统设计方案
- [x] 产出第一个HTML交互式学习系统原型
- [x] 提炼设计方法论和模板规范
- [ ] 让真实学习者体验，收集反馈
- [ ] 基于反馈迭代第二版
- [ ] 再做1-2个不同类型的课程（验证方法论的通用性）

**这个阶段的关键产出：**
- 经过验证的学习系统设计方法论
- 可复用的HTML模板和技术规范
- 2-3个不同类型的课程原型

**不做的事：**
- 不做agent嵌入（先把学习系统本身做到位）
- 不做自动化生产（先手动，提炼经验）
- 不开放给其他老师（先自己把流程跑通）

### Phase 2：角色+Skill成型，半自动生产（中期）

**目标：** 把手动打磨的经验沉淀为角色+skill，开始邀请老师使用。

**具体动作：**
- [ ] 把打磨经验变成TeacherYo课程设计师的角色定义和skill
- [ ] 用新素材测试角色：输入一份转写→角色输出设计方案→人工审核质量
- [ ] 迭代角色能力直到产出质量稳定
- [ ] 开发创作者后台（上传→协作→预览→发布的流程）
- [ ] 开发课程教师agent的嵌入能力（浮窗+context管理）
- [ ] 邀请2-3位老师试用，收集反馈
- [ ] 开发学习系统的学生端体验（进度保存、输入持久化、agent交互）

**这个阶段的关键产出：**
- 可用的课程设计师角色产品
- 创作者后台MVP
- 带agent浮窗的学生端体验
- 5-10门不同老师的课程

### Phase 3：平台成熟，规模化运营（远期）

**目标：** 角色+skill足够成熟，受邀老师可以自助完成课程生产。

**具体动作：**
- [ ] 角色能力持续迭代，减少人工终审的必要性
- [ ] 扩大邀请范围，建立创作者社区
- [ ] 课程设计师角色独立售卖/授权给其他平台
- [ ] 探索"智能体实时生成HTML"的更高级形态
- [ ] 建立学习效果评估体系

## 七、关键风险和应对

### 风险1：学习系统的"自动生成"质量天花板

**问题：** 学习系统设计的核心判断力（什么时机给什么、决定不讲什么）高度依赖经验。角色+skill能否达到足够的判断力？

**应对：**
- 不跳过Phase 1的手动打磨阶段
- 多做真实案例，让方法论足够具体和可操作
- 角色产出的是"草案"而非"成品"，老师确认和微调是必要环节
- 持续迭代：每一次生产都是角色学习的机会

### 风险2：课程教师agent的质量控制

**问题：** 从转写自动生成的教师分身，可能偏离老师真实观点，损害老师个人品牌。

**应对：**
- agent的角色定义必须经老师本人确认
- agent明确标注"非完全体"——只覆盖这节课的内容范围
- 设置"不确定时引导咨询"的兜底机制
- 老师可以随时调整agent的设定

### 风险3：邀请制的增长瓶颈

**问题：** 邀请制意味着增长速度受限于你的筛选速度。

**应对：**
- 早期这是优势不是劣势——质量比数量重要
- 中期建立"创作者申请→审核→通过"的标准化流程
- 远期可以开放"老带新"——已有创作者可以推荐新创作者

### 风险4：老师的参与意愿

**问题：** 老师可能觉得"上传素材+确认方案+微调"还是太麻烦。

**应对：**
- 让体验尽可能轻：老师只需要做自己最擅长的事（讲/聊）
- 让价值感尽可能强：明确告诉老师"你的分享会变成一个比视频课好10倍的学习体验"
- 让结果可见：老师能直接看到学生的学习反馈
- 让收益可期：课程产生收入，老师分成

### 风险5：角色产品被抄袭

**问题：** 一旦方法论公开（或被逆向），别人也可以做类似的课程设计角色。

**应对：**
- 真正的壁垒不是方法论文档，而是**从大量真实案例中积累的经验和迭代**
- 角色的质量取决于它"见过多少种素材、踩过多少坑"，这是时间壁垒
- 平台的网络效应：老师+学生+课程的积累是竞对无法快速复制的
- 持续迭代：方法论本身在进化，静态抄袭没有意义

## 八、与PromptX的技术对接要点

### 需要PromptX支持的技术能力

| 能力 | 优先级 | 说明 |
|------|--------|------|
| 学习系统HTML模板引擎 | Phase 2 | 基于设计方案自动生成HTML，支持模板+内容填充 |
| Agent浮窗组件 | Phase 2 | 前端对话组件，支持context注入、流式响应 |
| 创作者后台 | Phase 2 | 上传→角色协作→预览→发布的完整流程 |
| postMessage通信增强 | Phase 1 | 外壳页面与学习系统的双向同步（进度、模块切换） |
| 学习进度持久化 | Phase 2 | localStorage或后端存储，支持断点续学 |
| 学习者输入跨模块引用 | Phase 1 | 模块一的输入在后续模块中被引用展示 |
| Agent context管理 | Phase 2 | 课程内容的结构化存储+检索，控制token消耗 |
| 邀请制权限系统 | Phase 2 | 创作者身份管理、发布审核流程 |

### 当前技术架构（已有）

- 外壳页面：SPA结构，JS控制路由
- 课程内容页：独立HTML，通过iframe嵌入外壳
- 两者通过postMessage通信
- 纯前端，无后端依赖

### 需要新增的技术架构

- Agent层：需要后端API（大模型调用）
- 创作者后台：需要用户系统、权限管理
- 内容管理：课程元信息、发布状态
- 存储：学习进度、用户输入
